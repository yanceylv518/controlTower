# 全量归档统一任务操作说明

2026-09-21，本地实现，未发布或部署。本文替代此前要求用户逐日补齐、核验、封存，以及“旧月表尚不能接入”的操作限制。底层核验和封存约束仍见 [P4](archive-p4-operations.md)。

## 操作方式

1. 升级配套 Server 和 Agent，保留现有受保护配置中的源只读连接、归档写连接及 `CT_LOG_ARCHIVE_ENABLED=true`、`CT_LOG_ARCHIVE_MANAGED=true`。Server 启动自动执行 CT **090**；归档库为 **001–025**。rc128 不包含本次自动接入补修。
2. 在页面选择执行 Agent 并开启归档。无需手填站点/数据集/代际 ID，无需运行 `-archive-prepare` 或手动注册。已处于启用状态的旧托管归档会自动进入接入流程。Server 等待旧托管写入租约结束，持久保存身份并授权准备；Agent 识别已有身份、检查并迁移表结构、回报指纹，Server 自动绑定采集数据集并启用全量任务。失败后使用同一身份重试，重启不生成新身份或清空游标。
3. 自动接入保留旧月表原始日志，统计按原统一任务分批重建。Agent 写账号必须具备所需建表/迁移权限；源 `logs` 仍需日期扫描所需 `(created_at,id)` 索引，月表结构匹配且为 InnoDB。独立运行、不参与 CT 租约的旧写者不能靠此协议隔离，不应与托管归档共用目标。Server 专用只读连接不再是采集启动前置条件；独立验真/归档读取仍需其原有权限检查，自动绑定不开放归档出账。
4. 打开日志归档，选择正确执行 Agent。在“任务与策略”按实际情况声明源历史完整保留、仅追加、超过延迟窗口不再补写，且未归档数据不清理。默认不勾选；没有该声明也可归档和补齐，但不会自动封存。不能把当前扫描一致当作历史完整保留证据。
5. 在“全量归档任务”点击“启动归档”（恢复时为“继续归档”），**不用选择日期**。页面显示阶段、观察到的最早日期、当前处理日期、已接入行数、已封存/受阻天数。受阻项展示最早 20 天及原因；修复原因后可统一重试。

暂停保留目标端游标和子阶段，下次启用接续；服务重启或 writer epoch 切换也按持久状态恢复。运行中不能修改历史声明，核验/封存的冻结声明也不能通过暂停改写。调整普通批次参数和统一重试会更新配置版本，受阻日期由调度器重新处理。

页面以 `prepare_phase` 区分检查归档库、等待授权/旧租约、迁移表结构、等待绑定；失败使用独立错误码展示并自动退避重试。身份、来源或结构冲突不会自动覆盖；暂停不丢弃待准备身份。新 Agent 连接旧 Server 时只等待升级，不回落旧增量写入。

旧归档准备进度补充（rc129 后，本地待发布）：`reset_state/reset_daily/reset_monthly` 明确展示为清理旧贡献记录、旧日统计和旧月统计，完成后 `import_target` 读取已有月表重建。`workflow.preparation` 保存最近准备批次的阶段、表、游标、已记录处理量、最后一批处理量、提交批数、起始记录时间及最近提交时间；与实际清理/接入在同一事务保存，失败回滚，重启接续，无新增迁移或全表计数。计数仅涵盖配套升级后该阶段记录到的工作，不补造此前处理量或剩余百分比。阶段切换时标注上一阶段最后记录，进入逐日阶段后不再用准备批次判断当前进度。旧 Agent 缺少明细显示“尚未上报”，不显示假零；Server 和 Agent 需配套升级以保留新增字段。页面独立比较批次提交时间与心跳，停用、离线、错误、配置未确认和读取失败优先于近期提交提示；长时间无新提交只提示待核实，不直接断言卡死。

旧按日对账模式在租约排空后自动转换为全量任务，不遗留对账ID阻塞初始化。若已接入新版数据集但仍有独立补齐、核验或封存任务处于执行/重试中，会明确提示先完成原任务；不丢弃在途任务或绕过冻结约束。身份/来源冲突以具体错误保持上报可见，不将业务拒绝伪装为Agent离线。

## 自动执行链路

每日明细补充（rc129 后，本地待发布）：全量模式开放“每日数据”，按月展示全月日期、已统计原始/请求/错误日志数、最近处理阶段、受阻原因及明细采集时间。清理期间隐藏旧统计；接入旧月表期间明确标为重建中的部分计数，不将无上报显示成零，也不把旧站点回执混入当前数据集。日期详情区分状态采集时间和日期任务结果提交时间，未开放归档出账。

Agent 在原有约 30 秒检查周期中读取归档库日统计、日期目录和日期任务表，按日期主键每页最多 100 天循环上报；各输入查询最多读取 101 行，不扫描源库或原始日志月表，不修改归档游标。超过 100 天时，一轮明细更新需要多个周期；暂停时仍可读取状态，且不会启动归档写入。读取失败保留已有明细并提示，页面每 15 秒读取服务端缓存。Server 自动执行新增 CT **090** 缓存迁移，按数据集、工作流和日期隔离，仅接收有效执行节点的上报；归档库迁移仍为 **001–022**。需配套升级 Server 和 Agent，原 rc129 和此前 progress.1 本地包不包含每日明细。

`分批接入已有归档 → 最早日期分批读取/写入/回读校验 → 归档库日终核对 → 封存 → 下一日期`

- 起点取源日志与归档日期中可观察到的最早日期，不由用户输入。历史已被源和归档同时删除的区间无法凭空恢复，也不能由最早日期证明不存在更早数据。
- 新旧库均先检查身份、结构与写者授权。无现代 checkpoint 的纯旧月表允许统一任务接入；有现代版本/回执却丢失 checkpoint 的损坏库拒绝重置。
- 旧 `logs_YYYYMM` 和 `logs_undated` 按有界页读取，原始日志不重写。贡献台账、旧日/月统计分批重建，游标与统计在同一目标事务提交，重启不会重复累计。重建期间统计可能不完整。
- 扫描源时，同 ID 且内容一致跳过原始写入；缺失记录补入，变化记录修复并保存审计；源已经删除的目标日志保留，相关日期差异受阻，不能自动删掉或算作完整。
- 正常按最早日期向前推进，当前日期补齐/核验/封存后进入下一天；受阻日期保留原因并继续后续日期。跨日修正可能先使旧日期差异受阻，读到新日期后建立关联并共同复核。追赶历史期间不另起 ID 增量扫描，新增数据等待时间推进到其日期。当天读取仅到源时钟减归档延迟，保存 `(created_at,id)` 游标，空轮询不写回执；日期结束且超过延迟后，先结束当日流，再新建一次从日初开始的收尾补齐，捕获游标之前的迟到 INSERT。收尾完成后不再读源日志核验。已经结束的历史日期第一次补齐就可产生完整日证据，无须额外收尾扫描。空日期也需来源与稳定性证据。
- 跨日期修正自动收集关联日期，逐一核验后共同发布不可变版本；单组最多 31 天，关联回执读取超过 4096 条会受阻，需运维检查。旧发布版本保留。
- 完成历史推进后持续采集；目标 revision 改变会再次调度，取消默认近期 7 天周期复查。尚未结束的关联日期每隔至少 6 小时重试。此机制不是任意历史改写的 CDC；更久远的源端静默修改不保证自动发现。
- 主任务抑制 CT 旧独立日期任务派发；切换时有正在运行/等待重试的旧任务会冲突，需先处理。旧排队任务保留但不与全量任务竞争写者。已启用全量模式不能切回旧调度模式。

## 2026-09-21 源库减压修正

取消独立全历史 `source_scan` 以及日期处理期间穿插的 ID 增量扫描，不再两条路径重读同一历史；旧持久 source_scan 状态只做状态转换，已有核验/封存步骤继续恢复。首次发现最早日期使用日期索引取首条并持久保存，后续不重复发现。每个工作流批次（包括补齐、核验）均遵守配置的执行间隔，默认 30 秒，不再固定 2 秒推进；行数、字节预算和查询超时继续约束每页。此前将近期复查降低为至少 24 小时一次；本次追加式归档进一步取消了该周期复查。

源日期必须可排序：若存在 NULL/非正 created_at，索引检查发现后明确 source_invalid_date 阻断，避免时间游标静默遗漏；既有归档 undated 仍保留。此版本没有自动按源 CPU/负载退让，也没有生产负载实测。当前默认核验只读归档库；当天日终收尾和失败重试仍可能重读源日志，不能承诺零影响或所有日志只读取一次。降低压力会延长首次追赶耗时，应保证源保留期足以覆盖追赶过程。

前一轮逐日减压未新增迁移；本轮追加式校验新增归档库 022，原始日志、封存版本及旧 ID checkpoint 均保留；全量模式使用日期子任务游标，旧 ID checkpoint 不用来推断全量进度。

## 2026-09-21 追加式归档与校验

默认全量流程使用 `copied_source_paged`：源数据每页读出后，沿用已有事务内原始行回读比较（包括跳过写入的一致行），同时保存源摘要和逐 ID hash，数据/统计/证据/回执/游标一起提交。源证据来自实际读取，不能由归档库倒推。摘要保留全部字段、NULL、精确整数、时间与 ID 顺序，不能只用 COUNT 或 quota 相等作判据。

日期补齐完成后只扫描归档月表，逐 ID 与本轮源证据比较，发现 missing/different/extra；复用既有 revision/lease/assurance 门禁及不可变封存。新方法标识明确区别于 `stable_window_paged`，后者只保留给原有独立显式核验接口/历史记录，不再由默认全量流程调用。内部 target_second 阶段编号沿用已有存储槽位，不表示新方法进行了两轮目标扫描。

运行中旧日期任务如果没有022捕获证据，会新建日期任务重扫一次，不能伪造来源摘要；已经开始的旧封存构建继续恢复。已封存日期不再定期读取源库。目标修订变化或受阻后重试仍会触发对应日期补齐；未发现的源端历史 UPDATE/超窗口迟到不承诺自动检测，也不把新方法解释成源库一致性快照。

在仅追加、迟到有界、未归档日志不清理的运维约束下提供完整性保证；尚未确认这些约束时继续归档但不自动封存。生产数据规模/负载未验收，无binlog/副本依赖，无源端写入。

## 数据结构与接口

| 存储 | 本次内容 | 用途 |
| --- | --- | --- |
| 归档库 `archive_workflow`（020） | singleton_id、state_json、updated_at | 一个数据集的主任务、旧月表游标、下一日期、核验/封存子任务和关联日期组 |
| 归档库 `archive_workflow_days`（021） | log_date、state、revision、config_version、error_code、updated_at | 每日处理结果、修订号与受阻重试依据 |
| 归档库 `archive_scan_evidence`（022） | task_id、attempt、run_id、scan_json、last_batch_id、completed、updated_at | 与归档页原子提交的来源摘要和核验运行绑定，逐行hash复用archive_reconcile_issues |
| CT 既有站点配置/状态 JSON | full_history、history_immutable、workflow | 控制授权、能力和进度镜像；不复制原始日志 |

Agent 上报 `full_history_workflow_v5` 能力，Server 只有在绑定数据集且 Agent 支持时开放 `capabilities.full_history`。启停沿用站点配置 PUT，设置 `full_history=true`，无需 from/to 日期；状态新增 workflow。旧 Agent 不获得全量写授权。新表由 Agent 使用，Server reader 无需额外直接 SELECT 权限。

## 验证与限制

### 操作诊断与日历（本地未发布改动）

归档总览新增完整流程及当前操作卡片：先说明业务动作，再显示源库/归档库、具体表、处理日期和操作时间。操作在执行前通过独立控制轮询上报；只有事务提交后才更新准备批次计数。操作返回与批次提交分别展示，不由心跳推算完成率。

结构化诊断保留出错操作、MySQL 编号、SQLSTATE、可定位的日志 ID/字节数、发生时间和重试时间。不传递原始驱动消息、SQL、连接密码或日志内容。权限、认证、重复键、锁超时、死锁、连接异常与数据差异分别解释；未归类错误明确说明证据不足，不猜测原因。旧 Agent 没有这些字段时显示信息不足。

总览与每日数据均可用日历查看每天最近采集的结果，点击日期打开明细。缺少记录显示未知，部分重建数量不等于全天总量；暂停、上报过期、读取失败不把旧快照描述为当前执行。已封存只代表该日期最近上报的版本。

已通过 Go 测试、真实 MySQL 回滚及状态往返测试、前端测试和构建，以及桌面/窄屏浏览器检查。本地示例截图使用模拟数据，不代表生产状态。生产尚未升级这批改动。

四任务模式已在本地接入独立开关、采集范围/顺序、按日整理后校验及迟到写入失效，见 [四任务实现与升级说明](archive-independent-tasks-design.md)。需配套升级 Server 与 Agent 并显式切换；原有配置仍走旧串行工作流。日历已另行显示来自原始月表的真实计数快照及统计时间。

本机隔离 MySQL 已验证旧月表复用不重写、缺失补入、变化审计、统计重建、源已删记录保留受阻、跨日共同封存、epoch/重启接续、声明变更重试和近期低 ID 修正；CT 实库验证能力门禁、进度回读、暂停及旧队列隔离。Go 质量门及 Web 类型/构建与页面相关测试通过，细节见[交接](ai-tasks/2026-09-20-log-archive-billing-design.md)。

生产实际数据规模和索引成本仍需部署后验收。本轮不生成归档账单：`archive_billing=false`，P6 的固定归档输入及完整生成/恢复/下载链路仍待实现。
