# 设计：核对账单（对账）

日期：2026-08-07。状态：**讨论稿，待拍板**（拍板点见 §6）。

2026-08-07 讨论收敛：L3 与阈值告警均后置（用户认可）；**用户补充：阶梯计价已上线但基本无配置**——首版分类器简化为三类（缓存写政策/异常单/残差），阶梯与价格配置差并入残差兜底（其恒零的现状本身就是对账要守护的性质：残差≠0 即漂移信号）。首版=L1 差额列+合计卡+L2 三类标签+CSV。

## 1. 目标与定位

回答三个递进问题：**CT 算的账与 newapi 实际扣的钱差多少 → 差在哪（哪个用户/模型/天）→ 为什么差（哪个费率项）**。把上线清单里"抽两用户对账"的人工动作变成系统化、可下钻、可解释的常规能力。

口径基线：对账在 **USD/quota 基准**进行（显示层汇率不参与）；范围=消费账单（type=2），充值/退款不进（既有拍板）；异常单单列（CT 不计费但 newapi 扣了钱，差额已知且应显式呈现，不混入"未解释差异"）。

## 2. 数据基础（全部已有，无新采集）

| 数据 | 来源 | 用途 |
|---|---|---|
| newapi 实际扣费 | 聚合行 quota 列（billing_daily_versions，随账单生成落库） | 事实值 |
| CT 计费金额 | 查询时现算（CT 价/回退价 × 泳道） | 对比值 |
| 逐请求实际倍率 | logs.other 五倍率（184ad75 已提取） | 请求级归因 |
| 异常单实际扣费 | billing_anomaly_orders.actual_amount | 已知差额项 |

## 3. 三层结构

### L1 汇总层（纯 CT 本地，零生产库压力）

- 账单页/对账页：每用户增"实际扣费（quota 换算）/ 差额 / 差异率"列；
- 全站对账卡：区间总差额、差异率、差异分类占比（见 §4）、Top 差异用户与模型；
- 数据源=聚合行，现算即可，随 summary 缓存走。

### L2 日×模型层（纯 CT 本地）

- 差异明细表：day × model × group → CT 金额、quota 换算金额、差额、**差异原因标签**（§4 分类器输出）；
- 入口：从 L1 用户行下钻，或对账页直接按模型聚合。

### L3 请求层（按需回读生产库，限速）

- 对指定用户/模型/日，逐请求用行内倍率重建 newapi 实际单价，与 CT 计费逐项（输入/输出/读/写/分组）对比，输出差额最大的 N 条及逐项差异；
- 复用账单生成的限速分页（CT_BILLING_PAGE_PAUSE），按需触发不常驻；
- 这是"为什么差"的最终解释器：能精确指出"差在缓存写价"或"差在分组倍率"。

## 4. 差异分类器（设计核心）

L2/L3 将差额归因到互斥类别，按优先级判定：

1. **异常单**：actual_amount 合计（已知，单列）；
2. **缓存写政策差**：行内有 cache_creation_ratio（newapi 收了写费）而 CT 按 0 计——用户拍板口径产生的**有意差异**；
3. **阶梯计价差**：CT 阶梯价与 newapi 平价的差——CT 补齐能力产生的**有意差异**；
4. **价格配置差**：CT 配价 ≠ 行内实际倍率换算价（折扣定价或配置漂移——是否有意由用户判断，展示两个价）；
5. **分组倍率差**：CT group_ratio ≠ 行内 group_ratio；
6. **未定价模型**：CT 无价走回退，差额=回退口径与实际的残差；
7. **未解释残差**：以上都排除后的剩余（含舍入），超过阈值（如 0.5%）标红——这是真正需要人看的信号。

关键性质：1-3 类是**制度性差异**（预期内，对账报告里应显示但不报警）；4-7 类才是**漂移信号**。

## 5. 产品形态

- **对账页**（或账单页新 Tab，见拍板点）：区间+站点选择 → L1 对账卡+用户差异列表（按差额排序）→ 点行下钻 L2 → L2 行触发 L3 请求级分析（异步任务，复用导出任务框架）；
- **对账报告导出**：CSV（L1+L2 平铺+分类小计）；
- 前置条件与账单一致：该区间已生成账单（绑定 job 版本，与账单页同语义）。
