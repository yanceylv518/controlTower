# NewAPI logs 归档到另一套 MySQL RDS

Agent 将源库 `logs` 全部类型、全部字段按日志时间复制到专用 MySQL 5.7/8.x 数据库的 `logs_YYYYMM` 月表，同时维护日/月整体统计。源库只读，不删除源日志。默认关闭，独立连接池与后台任务，不使用监控采集游标、不经过 Control Tower Server。

## 准备目标库

目标必须是当前 NewAPI 实例专用的归档数据库，不能复用其他实例或线上 NewAPI 正在写入的数据库。只运行一个归档 Agent；负载均衡场景在其中一个节点启用。

1. 在目标 RDS 创建专用数据库，字符集和排序规则与源库一致。
2. 通过源库 `SHOW CREATE TABLE logs` 在目标库创建同结构 `logs` 模板。Agent 不向模板插入数据；按需通过 `CREATE TABLE ... LIKE logs` 创建月表，并创建统计和去重辅助表。不要导入触发器。
3. 目标表必须使用 InnoDB，主键为 `id`，不能有其他唯一索引。字段名称、顺序、类型、可空性、字符集、排序规则及 EXTRA 必须与源表一致；暂不支持生成列。源表升级后，先同步目标表结构。
4. 源账号只需读取 `logs` 和可见元数据；目标专用库账号需 `SELECT, INSERT, UPDATE, DELETE, CREATE`。DELETE 仅用于源日志时间被修正后，将对应归档从旧月表移走，不删除源数据。所有表必须是 InnoDB。配置 RDS 网络访问和 TLS，使用主实例写入端点。

## 配置

在服务器 `/etc/control-tower/agent.config` 中增加：

```ini
CT_LOG_ARCHIVE_ENABLED=true
CT_LOG_ARCHIVE_DSN=archive_writer:REPLACE_PASSWORD@tcp(archive-rds.example:3306)/newapi_archive?tls=true&charset=utf8mb4
CT_LOG_ARCHIVE_BATCH_SIZE=500
CT_LOG_ARCHIVE_INTERVAL_SECONDS=30
CT_LOG_ARCHIVE_DELAY_SECONDS=300
```

源连接复用 `CT_LOG_DSN`，归档另外开一个最多 1 个连接的池。目标池也最多 1 个连接。现有监控或独立企业微信告警配置仍然需要保留。`CT_LOG_COLLECT_ENABLED=false` 只关闭监控日志采集；显式启用归档后仍读取源库。

先用新版本二进制执行 `control-tower-agent -config /etc/control-tower/agent.config -preflight`，再重启服务。预检只读，检查连接、源目标身份、目标引擎和表结构；写权限在首批归档时验证。`CT_AGENT_RUN_ONCE=true` 只处理一批归档，不会自动搬完全部历史；归档错误记录在 Agent 日志中，不改变监控任务的退出结果。

## 运行语义

- 第一次从 `id > 0` 开始补齐现存历史，每次最多配置的批量行数，之后持续增量。默认吞吐上限约 1,000 行/分钟（不含执行耗时），高流量实例需要调整间隔、批量并观察追赶情况。
- 原样复制包括 `content`、`other` 在内的字段，保留 NULL 和文本；不经过监控脱敏/抽样。目标库应采用与源日志相当的访问控制。
- 月表明细、去重辅助记录和日/月统计在同一目标事务提交成功后，才将游标原子保存至 `CT_DATA_DIR/log-archive-monthly-v1-<身份摘要>.json`。身份包含实例 ID、源和目标地址及库名，不含密码。失败下次重试；提交成功但保存状态失败时会重放，按主键更新同一行，不重复累加统计。
- 默认只归档 5 分钟以前的日志，`CT_LOG_ARCHIVE_DELAY_SECONDS` 可设为 60～86400 秒。用源 MySQL 的 `UNIX_TIMESTAMP()` 计算截止时间，避免 Agent 时钟偏差。按主键查询一个有界批次，在内存遇到第一条未满延迟时间的日志就停止；不会过滤掉它后继续推进到更大 ID。后续批次从原游标继续，因此时间戳乱序也不会跳过已可见的新日志。
- 不再每日全表重扫，不自动同步已经归档的历史修改；旧检查点的 completed_at 字段不再触发重扫。按照追加写日志的使用方式运行。延迟窗口用于避开正常并发写入，不保证捕获超过窗口才提交、且时间戳很早的事务；本功能不是数据库 CDC。
- 每批检查同结构和严格 SQL 模式，避免类型不匹配被静默截断。源目标数据库通过 MySQL `server_uuid` 和库名检查，阻止指向同一源库；暂不支持 PostgreSQL 或 MariaDB。
- 归档每批最多运行 60 秒。连接、查询、写入或状态错误仅在 Agent 日志记录阶段信息，不打印 DSN、密码或原始日志。持续运行模式下重试，不阻塞监控和告警。
- 本功能不会删除任何源日志，也不会同步源库删除。不要在归档追平、补扫并核验完整性前用其他任务清理源日志。

## 验证

每批归档自动校验：在目标事务提交前，按本批 ID 从对应月表读取全部源字段，与内存中已经读取的源日志逐行对比，核对 ID 集合和全部字段（区分 NULL 与空字符串）。不再次查询源库，不用 COUNT 或整表 checksum。校验在每个受影响月表增加一次目标主键读取，增加目标库读取和事务时间。

发现缺行、重复 ID、字段不一致或校验查询失败时，明细、辅助记录和日/月统计一起回滚，不推进游标，下次重试。错误不记录字段值。提交成功并保存检查点后，`last_verified_at` 和 `last_verified_rows` 记录最近一批通过写入校验的时间和行数。

该功能验证的是本批明细写入一致性，不是整库历史完整性对账，也不会检测归档后被人工修改/删除的数据或重新核算全部日/月统计。另有页面手动触发的按日明细完整性对账，见下文。

查看 `journalctl -u control-tower-agent` 中的 `log archive: committed N rows` 或归档失败信息；源库持续写入时，不应只用 `MAX(id)` 相同判断完整性。对已经稳定的时间区间，核对源目标行数、ID 集合和关键字段抽样。月表、统计和辅助表是关联数据，不要单独清空或编辑其中一部分；需要重建时应整体重建归档数据，并在源日志仍完整保留的前提下重置对应检查点后重放。

## 月表和日/月统计

固定按北京时间 UTC+08:00、源 `created_at` 时间划分，和 Agent 主机时区、归档执行时间无关。

| 表 | 用途 |
| --- | --- |
| `logs_202608`、`logs_202609` 等 | 月度原始明细 |
| `logs_undated` | created_at 为 NULL、0 或负数的日志 |
| `log_daily_stats` | 每日整体统计，period_key 如 `2026-09-01` |
| `log_monthly_stats` | 每月整体统计，period_key 如 `202609` |
| `archive_log_state` | 每条日志 ID 上次的统计贡献和日期，用于重复归档去重及历史修正 |

没有有效日期的统计使用 `period_key='undated'`。第一版每天/月各一行，不增加用户、渠道或模型维度：

- `log_rows`：全部类型日志行数。
- `request_rows`：type 2 和 5 的行数。
- `consume_rows`：type 2 消费日志数，不将其称为严格业务成功数。
- `error_rows`：type 5 错误日志数。
- `prompt_tokens`、`completion_tokens`、`quota`：type 2 和 5 对应原始字段之和，其他类型不计入，避免充值记录影响用量。quota 是配额单位，不折算货币。

统计字段为 DECIMAL(38,0)，差额计算不经过浮点数。日/月统计只反映已归档数据，首次尚未追平时不代表源库完整统计。

明细按月份分组、多行参数化写入，每条 SQL 约按 1 MiB/30,000 参数拆分，单条超大日志单独发送并受 MySQL 包大小限制。整个批次目前仍只有行数限制，没有字节硬上限。每批读取这些 ID 的旧贡献，在内存合并“新贡献减旧贡献”，各日期/月更新一次统计；不重新扫描源库或全表重算明细。代价是目标库增加一份按 ID 保存的贡献记录。

重试或补扫相同日志时差额为零；旧字段修正时按差额修正统计。created_at 跨月修正时，事务内删除旧月的该条归档、写入新月并调整两侧统计。DDL 在事务开始前执行，初始化失败可能留下空表，但不会推进游标。

源表升级后须同步模板及已有月表，不能只改模板。月表自动清理保留期尚未实现，手工删除月表会使统计和辅助记录失去对应关系。

```sql
SELECT * FROM logs_202609 WHERE id > 100000 ORDER BY id LIMIT 100;
SELECT * FROM log_daily_stats
WHERE period_key >= '2026-09-01' AND period_key < '2026-10-01'
ORDER BY period_key;
SELECT * FROM log_monthly_stats
WHERE period_key <> 'undated' ORDER BY period_key;
```

月表版使用新的检查点文件名，升级后从源库重新补齐月表和统计。旧目标 `logs` 数据保留，只用其结构作为模板；若源库已缺少历史，应另行迁移旧目标数据。重新补齐会增加读取量，应在低峰启用。

CT 管理页、独立控制轮询、短期执行授权及托管模式失败退避已经实现。批次字节硬上限、元数据检查缓存等负载优化仍未完成。

## CT 页面管理

入口：系统管理 → 日志归档（`/log-archives`）。权限为 `archive.manage`；完整管理员默认可用，受限管理员需要分配该权限。CT 启动时按现有迁移流程应用 `071_log_archive_control.sql`、`072_log_archive_sites.sql` 和 `073_log_archive_days.sql`，需要发布新的前端资源。旧实例策略迁移为暂停的站点策略，重新选择执行节点后再启用。

Agent 保留本地源/目标 DSN，并设置：

```ini
CT_LOG_ARCHIVE_ENABLED=true
CT_LOG_ARCHIVE_MANAGED=true
```

必须配置 CT URL 和实例专用 Agent Token，不支持全局旧 Token 或 RUN_ONCE。首次托管启动等待 CT 启用，不自动沿用本地 enabled 开始归档。设置 managed=false 则恢复原本本地模式，请避免在仍需受 CT 暂停管理时这样回退。

页面只展示顶部当前选择的站点；每个站点配置一个执行节点和 Agent，候选节点限定在该站点内。显示目标是否配置、期望状态、已应用版本、提交 ID、最近成功时间、写入校验和错误。源目标连接密码不上传。配置更新使用版本校验防止覆盖，写入操作审计；同一站点同一时刻只允许一个有效启动会话执行。

每日任务以“站点 + 北京时间日志日期”保存一条记录，可按月份查看。同一天的后续批次更新这条记录，归档仍持续增量执行，暂停作用于整个站点。记录在该日期第一批成功归档后出现，没有日志的日期不创建空任务；历史日期也可能继续补入，页面“已归档”不表示已经完成源库完整性对账。

每日条数读取目标库已有日统计的累计值，在明细事务中获取，提交后随检查点保存，再通过控制轮询上报 CT。重复上报替换累计值，不累加；不增加源库查询。CT 按站点和月份索引读取记录。升级前已归档日期不会自动回填 CT 记录；无有效日期的日志保留在目标 undated 表及统计中，不显示在月度任务列表。

归档控制独立于监控心跳，每 15 秒提交一次轮询，通过[统一控制入口](agent-control-poll.md)与容器日志的待发送请求合并，最多增加约 1 秒合并等待。归档执行和控制轮询独立，托管批次超时 45 秒；正常情况下暂停领取最多等待约 15 秒加当前批次耗时，页面确认还需下一轮状态上报及刷新。暂停只停止新批次，不中断正在提交的事务。CT 不可达时不会开始新批次，不回退成本地归档。

每次允许执行都会发放 120 秒授权，Agent 在有效授权内串行处理批次，启动前须剩余超过 45 秒授权；轮询失败后不再启动新批次。批次最多 45 秒。CT 保留未到期会话以阻止重复进程同时执行，Agent 重启可能需要等旧授权结束。没有自动跨主机切换。每批结束后等待配置间隔，最低支持 2 秒，不再受 15 秒控制轮询周期限制；失败额外退避至最多 5 分钟。监控及告警使用原来的循环，不受控制接口故障阻塞。

发布顺序：先部署 CT 和迁移/前端，再升级单个 Agent、开启 managed，并在页面启用小批量验证。Go 与前端构建及模拟界面验证不代替真实 RDS 联调和源库负载验证。

## 手动按日完整性对账

先在当前站点暂停归档，等待 Agent 确认后点击“按日对账”。需要升级 Agent，旧 Agent 不支持启动此模式。选择已经结束且超过归档延迟窗口的北京时间日期；一次对账期间不再执行增量归档。按当前批量和间隔分别分页读取源 logs 和对应目标月表，按 `(created_at,id)` 游标顺序计算包含 NULL、二进制内容及所有原始字段的 SHA-256 摘要，同时比较行数。可发现缺行、多行和字段差异；不输出日志内容、不自动修复数据、不重算统计。

源库必须已有 created_at 开头的索引，Agent 校验后显式使用该索引；缺失时直接失败，不自动建索引。不对源表执行整表 COUNT，不维持跨批次长事务。目标月表不存在时按空集合参与比较。对账要求选定日期数据在执行期间保持不变；它不是两个数据库的同一时刻快照，期间若有外部写入、修改或删除，应在数据稳定后重新对账。

可暂停并继续同一次对账；重启时，未完成对账从该日期起点重新开始，已完成结果从本地恢复。当前页面保留最近一次对账结果，包含两侧行数和一致/差异/失败状态，没有逐行差异清单或多次对账历史。完成后仍停留在对账模式，点击“结束对账模式”，再启用归档。对账会增加所选日期的源库读取，应按需触发。
