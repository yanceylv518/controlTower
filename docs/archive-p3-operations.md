# P3 日期补齐、预算与覆盖目录

本阶段实现受预算约束的增量采集、近期轮转、指定日期补齐及覆盖观察接口。扫描完成只产生“待核验”或“零行候选”，不产生封存版本、正式核验结论或账单输入。P4–P6 仍负责核验封存、金额配置与归档出账。

## 升级与运行

1. 沿用 [P2 升级要求](archive-p2-operations.md)：先暂停、等待租约及当前批次结束，停止旧写入器并隔离旧写账号；源库始终只读。
2. CT 执行 **087**；Agent 用显式 `-archive-prepare` 将目标库升级到 **010**。009 新建 `archive_scan_tasks`，010 新建 `archive_ingest_issues`，001–008 校验和不改。常规 Agent 启动不会自动迁移目标库。
3. 更新 Server 与 Agent，等待 `date_backfill_v3` 能力和结构预检就绪。数据集仍需在“任务与策略”手动启用；暂停期间可排队，但不派发或执行补齐。
4. 通过下列接口登记覆盖证据、查看任务与重试。P3 提供后端/API；页面补齐按钮、队列和日期状态联调属于 P7。已绑定新版数据集返回 `date_backfill=true`、`coverage_catalog=true`，旧页面显示“等待页面联调”；`day_versions`、`archive_billing` 保持 false。

首次取得目标写入权时，只有经严格检查为空的目标才建立 `incremental=0` 权威起点。随后即使补扫先写入数据，增量仍从零前进；不使用 MAX(id)。旧数据导入仍按 P8 单独核验，不能用空起点绕过旧数据准入。

## 覆盖证据与策略

所有接口要求已有登录会话、`archive.manage`；写接口沿用 CSRF。路径中的数据集和 `site_id` 必须匹配。证据仅填写脱敏运维说明，不能填 DSN、密码或日志原文。

先 `GET /api/dashboard/archive-datasets/{dataset}/coverage-policy?site_id=...` 获取 revision，再通过同路径 PUT 保存。例如：

```json
{
  "revision": "0",
  "coverage_from": "2026-09-01",
  "source_retained_from": "2026-09-01",
  "evidence": "已核对该源代际的启用记录和日志保留设置；此日期起历史仍在源库",
  "recent_days": 7,
  "budget": {
    "max_rows": 500,
    "max_bytes": "4194304",
    "max_row_bytes": "4194304",
    "max_duration_millis": 30000
  }
}
```

这里的日期仅为接口示例，不代表已核验任何站点。`coverage_from` 是明确确认的目录起点；`source_retained_from` 是明确确认源历史仍可读取的起点，两者都不能从 MIN(created_at)、首次上报或一次空查询推导。Server 保存确认人、时间、证据和递增 revision，并执行版本冲突检查。

不确定源保留边界时留空 `source_retained_from`：扫描仍可复制可读数据，但结束后标记 `source_history_unknown`，不能宣称零业务或完整。早于已声明源保留起点的日期标记 `source_cleared`。这些是显式运维声明，系统无法仅凭当前源表证明历史从未清理；P4 还需完整性核验。

日期范围使用北京时间自然日 `[00:00, 次日00:00)`。今天和未超过源库延迟窗口的日期不能执行历史补齐。首版策略修改要求同时登记覆盖起点和证据；`recent_days=0` 可关闭自动近期任务。

## 指定日期、自动轮转与恢复

- `POST /api/dashboard/archive-datasets/{dataset}/backfill-tasks?site_id=...`，JSON 为 `{"request_id":"<非零32位小写十六进制ID>","date":"2026-09-18"}`。同请求 ID、同日期返回同一任务；同 ID 改日期拒绝。
- `GET` 同路径读取最近 200 个任务，包含状态、尝试、时间游标、累计扫描行/字节、耗时和固定错误码。
- `POST /api/dashboard/archive-datasets/{dataset}/backfill-tasks/{task}/retry?site_id=...` 显式重试 blocked/retry_wait 任务，递增 attempt、获取当前策略快照，并从该日开始重扫；不重置增量游标。

近期任务默认覆盖最近 7 个已结束日期，昨日优先，每日期最多每 6 小时开启一轮。新轮次使用新任务身份和新扫描起点，才能发现上一轮游标之前出现的迟到小 ID。近期窗口为运维初值，不是完整性保证；历史窗口之外的修改需指定日期补齐。手工队列优先，等待较久的近期任务提高优先级，正在执行的日期优先继续。

Agent 串行执行源读取，持续积压时每 3 批增量预留 1 批补扫；增量追平后让出下个扫描机会。满预算增量以 2 秒间隔继续，追平或遇到源延迟窗口则回到已配置间隔。行数、原始解码字节和耗时共同限制；实际行数取策略与原归档 batch_size 的较小值。超大单行阻断并记录源 ID/错误码/字节数，不跳过。字节指标为逻辑原始字段字节，不是网络或磁盘实际 IO；任务字段是当前 attempt 的累计值。

CT 保存调度意图；目标保存权威扫描结果。每个 `(task_id, attempt)` 使用独立 `(created_at,id)` 游标，分页原子提交原始数据、统计差额、日期修订、回执和任务进度；空页完成也要持久回执。重启、新 epoch 接管和临时故障自动重试保留同 attempt 游标。暂停停止新批次，已开始批次按租约边界处理；旧 epoch/会话/attempt 不能回写新进度。取得写入权失败时两个流共同退避，单个源扫描失败不长期阻塞另一个流。

源必须已有适合时间排序的索引：显式 `(created_at,id)`，或 InnoDB 的单列 created_at 索引结合 id 主键。缺失/不适用索引返回 `source_index_missing`，不自动给源库加 DDL。目标已有而源不存在的记录不会自动删除“对平”。

## 日期目录和异常

`GET /api/dashboard/archive-datasets/{dataset}/coverage?site_id=...&month=2026-09` 返回完整月份，日期状态包括未来、今天、起点之前的未知历史、待补齐、待核验、零行候选与阻断。任务进度属于观察信息，不是账单证据；正式版本计数和 verified_at 继续保持独立。

目标 `archive_days` 记录扫描相关状态，目录变化推进 catalog revision；Server 现有 `POST .../{dataset}/sync` 从专用只读连接同步整份目录。CT 中的全局阻断投影只有同步后更新，不能把旧缓存当作最新完整性证明。正式出账能力仍关闭。

目标 `archive_ingest_issues` 保存源 ID、错误码、逻辑字节数和解决时间，不保存日志原文。无效日期、未知收费类型非零 quota 仍阻断出账资格；修正原始行时更新贡献和问题状态。冻结日期、结构变化、目标游标/回执不一致都会拒绝危险推进，不能用重试跳过数据。

元数据完整检查使用 30 秒缓存，绑定身份指纹、结构指纹和迁移集合；检查失败或写入错误使缓存失效。显式预检仍执行完整检查。没有版本信号的外部 DDL 通过定期完整预检识别；源结构升级应按暂停、准备、重检流程完成。

## 验证边界

质量门为 `go vet ./...`、`go test ./...`；实库测试使用本机随机临时 schema 和只读测试账号，覆盖迟到小 ID、同秒分页、跨月、字节边界、故障恢复、租约接管、任务幂等和未知历史。验收结果见[任务交接](ai-tasks/2026-09-20-log-archive-billing-design.md)。

生产源规模、源索引执行计划、MySQL 5.7/8.x/MariaDB、真实 IO/锁竞争、物理断电及备份恢复仍需环境验收。没有实测固定吞吐承诺；没有执行生产迁移、启停、账单生成或部署。
