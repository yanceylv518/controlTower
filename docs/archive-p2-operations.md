# P2 原子归档写入与恢复

日期：2026-09-20。本阶段在 P0/P1 身份基础上实现可启停的新版增量采集。后续 [P3](archive-p3-operations.md) 已补入日期扫描、预算与覆盖观察接口；核验封存、历史金额配置及归档账单仍属于 P4–P6，相关出账/日版本能力为 false。

## 实际写入路径

1. Agent 通过现有认证控制接口上报 `foundation_v2` 与 `atomic_writer_v2`，确认站点、数据集、源代际和配置版本。
2. CT 对选定且就绪的实例/Agent 发放包含 session、配置版本、writer epoch 的短期授权。不同会话不得抢占仍有效的 CT 租约；过期接管提升 epoch。暂停不续租，不把尚未结束的旧租约提前当成已失效。
3. Agent 按请求开始时的本机单调时间计算授权截止，保留 30 秒余量；将剩余时间交给目标库认领写入。预检、网络和行锁等待都消耗该预算。不按反复使用的缓存响应重新计算 120 秒。
4. 目标库锁定唯一元数据行，绑定 epoch/session，使用目标数据库时间判断有效期。每批开始和提交前都检查；旧 epoch、不同 session 或失效授权不能提交。暂停/控制不可用时释放自身目标租约，不能释放后继执行者。
5. 从目标 `archive_checkpoints` 的增量游标读取源库延迟窗口内的有序前缀。一批目标事务包含：原始月表、跨月搬移、贡献与日/月统计差额、原文字节 hash、日 mutation revision/dirty、全局阻断计数、目标 checkpoint、批次 receipt。逐字段回读核验失败则整体回滚。

月表 DDL 必须在数据事务外完成（MySQL DDL 有独立提交语义），只创建空结构，不推进游标；进入数据事务后重新校验授权。锁顺序为元数据、排序后的日期、日志 ID 状态；变更跨日时同时锁旧日和新日。任何 freeze 标记都会阻止写入，包括过期但尚未完成恢复的标记；P4 再实现冻结恢复流程。

## 幂等与进度

- `batch_id` 绑定规范编码的 payload hash；NULL、空串和任意二进制字节保持区别，不使用会替换非法 UTF-8 的 JSON 字符串散列。
- 相同 ID、相同 payload 读取已有回执；相同 ID、不同 payload 拒绝。重复请求不重复累计、不重复增加日修订。
- 原始行只修改 `other` 等非统计字段，也会标记相关日期 dirty；完全相同行不改变修订。
- COMMIT 返回异常时查询归档库中的回执核实结果。连接仍不可用则报“结果未知”，下次从目标游标恢复；不会依赖本地成功标记去猜测提交是否成功。
- 本地 legacy checkpoint 文件不参与新版恢复。缺失、损坏或移动本地文件不改变目标游标。目标 checkpoint 必须与所引用 receipt 的游标一致，不一致时阻断自动运行。
- CT 只展示已确认的进度；目录仍由独立只读连接读取。相同会话丢失新 epoch 授权响应时可获取重传，旧进度不会因此被接收，未确认认领的重试不能延长原租约。

无法归期的行、未知类型且非零 quota 的行先按全局阻断处理；贡献状态记录每行的阻断标记，修正后通过同一事务更新计数。此阶段不生成核验结论或账单事实。

## 升级和启动

1. 保留[基础准备流程](archive-foundation-operations.md)中的源只读、专用目标库、固定身份、Server 专用只读连接和旧进程停用要求。旧二进制无法识别 epoch，必须停止旧写入器并隔离旧写账号。
2. CT Server 迁移至 **086**；归档目标通过显式 `-archive-prepare` 迁移至 **008**。新增 006 创建贡献台账基础结构，007/008 添加 raw hash 与 last batch ID；001–005 的已发布校验和不改变。ALTER 已成功但迁移回执丢失时，只接受精确匹配的已存在列。
3. 数据集注册后仍默认暂停。启动升级后的 Agent，等待其身份/结构预检通过并上报 atomic writer 能力。P1 旧 Agent 没有此能力，不能启动新版写入；新版 Agent 对旧 Server 的普通 Granted 标志也不会回退到旧写入器。
4. 在“日志归档 → 任务与策略”选定就绪执行节点并启用归档。沿用现有配置版本冲突保护；服务端再次验证能力与身份。看实际 applied version、状态、最近成功时间和游标，不以按钮点击结果表示批次已完成。
5. 暂停后等待当前批次结束；切换执行器还要等旧 CT 租约到期。新会话拿到更高 epoch 后，旧会话不能恢复写入。生产部署与真实启停需要对应环境授权；本次实现只在隔离测试环境验证，没有操作生产。

CT 与目标数据库时间各自判断各自租约；传输预算由单调时间消耗。停用、执行节点变化和再次注册不重置 CT epoch。CT/归档备份恢复造成代号不一致时应停止并核验，不能手工把目标 epoch 改小来绕过保护。

## 已有归档数据的边界

**没有新版权威 checkpoint，且目标已经有日志、台账、统计、回执或日期/版本数据时，P2 拒绝自动接管。** 不读取旧本地游标、不取 MAX(id)、不自动宣称历史完整。空结构且没有数据可以启动。已有 legacy 数据的候选游标、原始行和覆盖证据需要 P8 的显式导入/核验演练；目前没有“强制跳过”按钮。

目标 checkpoint 被误删也按上述规则停止；应从可信备份或显式恢复流程处理。本地文件丢失与目标权威数据丢失是两种不同故障。

## 验证与未完成项

Go 质量门为 `go vet ./...` 和 `go test ./...`。额外集成测试沿用仅用于本机测试的 `CT_MYSQL_TEST_DSN` / `CT_ARCHIVE_TEST_DSN`，创建独立随机 schema，模拟批次失败、COMMIT 响应丢失、冻结和跨月修正、并发会话、过期授权、错误回执与本地缓存丢失；不向生产注入故障。

物理断电、真实网络中断、生产负载/锁等待、生产 MySQL 版本与备份恢复尚需环境演练。增量游标只覆盖按 ID 扫描的前缀，迟到的小 ID 与历史修正由 P3 日期补扫补充；P4 再核验完整性。因此启动或扫描成功仍不代表已有任何日期可以正式出账。
