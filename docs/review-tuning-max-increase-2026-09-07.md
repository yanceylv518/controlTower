# 验收记录：自动模式单次上调上限（2026-09-07）

- 范围：`6d518f2 feat(tuning): limit automatic weight increases per cycle`（合并提交 `672fdc1`）
- 结论：**通过，验收修正一处 P2**（个位数权重永远升不了）。

## 变更

- 连续调权参数新增 `max_increase_percent`（默认 10，范围 1–100）：自动模式每轮评估把
  拟议权重的上调幅度限制在"当前有效权重 ×(1+比例)"以内，向下取整；下调与熔断置零不受
  限制；只观察模式仍显示不受限的目标值。当前有效权重优先取本系统最近一次成功写入
  （写入晚于渠道快照时），否则取快照值。
- 效果：恢复或大幅评估上调时逐轮爬坡（10% 时约 7 轮翻一倍，每轮 30 秒），每轮各写一次
  new-api；此前一次写到位。去重逻辑相应改为"从上次写入值继续爬坡"，测试已同步。
- 兼容：库里旧策略无该字段，`DecodePolicyJSON` 从默认策略起步再覆盖，解码得 10（烟测
  demo 站点实测）；前端加载也兜底 10。规则设置页新增"单次上调上限（%）"。

## 缺陷与修正（P2）

**向下取整让个位数权重永远升不了**：`floor(current×1.1)` 在 current 为 1–9 时等于
current，拟议上调被压回原值。new-api 渠道权重常见 1–10 的小整数，这类渠道一旦被
降权或熔断软启动后，自动模式再也升不回去。修正：每轮至少允许 +1，
`maximum = max(current+1, floor(current×(1+p/100)))`；回归测试钉住 1/5/9 三档必须
能升一步，6←5 不被拦。页面说明补"至少允许 +1"。

## 记档（P3）

- 爬坡期间每轮都写 new-api 并各记一条流水/审计，恢复大幅度权重时写入次数明显增多；
  比例可按站点调大。
- 上限按"当前有效权重"计算，若最近写入的确认回写与快照都滞后（Agent 命令路径未回执
  前），爬坡基线会暂时偏旧，最多多等一轮。
