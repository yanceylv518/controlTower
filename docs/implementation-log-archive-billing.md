## 1. 一期交付边界

一期必须完整交付：可靠归档 → 按日补齐/核验 → 固定版本 → 用户账单独立生成 → 文件下载。生产源数据库断开后，已有归档与配置证据覆盖的账期仍能查询历史用户、生成、重试和下载。

先使用现有系统账单模板，增加明确的模板/渲染版本与固定产物；用户 XLSX 上传模板属于另一项已设计功能，不作为归档首版依赖。以后接入上传模板继续复用同一账单计算快照。

一期保留现有实时日志查询、上游账单和旧账单兼容路径。新用户账单切入 archive 后不得自动回退线上。源日志自动删除、归档自动清理、冷存储、任意历史修改 CDC 和跨站点/跨源代际合并不纳入一期。

## 3. P0：先固定实现契约

工作项：

1. 列出字段契约：原始 logs → 不可变计费原文 → 标准化事实 → 现有 PagedLogRecord；标明 NULL、零、未知值、类型和精度。
2. 固定身份、状态与版本：dataset/generation、日 revision、day_version、catalog_revision、执行 epoch、parser/usage/计价/过滤版本分别负责什么。
3. 固定服务端出账判定：日志封存 + 配置有效期覆盖 + 对象身份明确 + 异常可处理。区间沿用北京时间 `[from,to)`，一期要求所有相交自然日已封存。
4. 明确数据源与计价方式是独立字段；老任务缺省明确映射 legacy_live，不能因升级被重新解释为 archive。
5. 建立脱敏合成样本：普通/表达式、缓存 5m/1h、图像/音频/按次、零价/零输出、坏 other/NULL、同秒多 ID、重复 request_id、小额精度、跨月/跨代际。
6. 形成环境核验表：真实日均/峰值行数和字节、源索引/清理/迟到约束、归档版本/容量/备份、Server 网络、历史 QuotaPerUnit/单位证据。未知项明确保留；本地实现可继续，生产启用需完成对应项。

改动入口：`internal/archivecontrol/contracts.go`、`server/internal/billing/jobs.go` 的契约及相关设计/测试样本；共享提取模块建议落在根级 `internal/`，不由 Agent 导入 Server 的 internal 包。

验收：逐字段映射可对照现有读取器；定义旧解析语义的回归样本；明确日“封存”不是自动“可出账”。本批不重写计费算法。

## 5. P2：先保证每批归档不漏不重

工作项：

1. 把权威 checkpoint 放进目标事务，与明细、贡献差额、统计和批次回执一起提交；本地文件仅作恢复缓存。
2. 保留现有事务内逐字段回读校验；失败回滚整个批次。
3. 增加 batch_id 与重放判定，提交响应丢失时通过目标回执确认，不依据 CT 的 last_id 跳过数据。
4. 执行者接管分配递增 epoch；每次目标事务锁定并校验 epoch/授权，增量、补扫、核验修复、封存写入均遵守同一规则。
5. 所有改变原始日志集合的写入递增受影响日 revision，并预先实现日期冻结标记的检查，包括旧库导入/修复入口；跨日修正必须两侧一起失效，为 P4 核验提供可信版本边界。P4 再接入冻结任务的完整生命周期。
6. 旧 checkpoint 的导入只作为待核验候选，不从 MAX(id) 推导历史完整性。没有可信游标时选择安全重放/按日补齐，不能静默越过缺口。

兼容门槛：epoch 只能约束遵守新版协议的写入器。启用新版数据集前必须暂停并停止所有旧/本地模式归档进程，确认旧事务已结束，撤销旧写账号或更换独立新版写账号，再启用新版唯一执行者。新版本本地模式不得绕过已托管数据集的控制规则。

改动入口：`agent/internal/logarchive/archive.go`、`monthly.go`、`verify.go`，托管循环及目标 store；CT 负责授权接管状态。

验收：在写入前后、COMMIT 响应前后、缓存保存前后注入故障；断点丢失、重复发送、两个进程竞争和过期会话均不重复累计或漏日志。真实 MySQL 验证事务/锁顺序，确认监控线程不被归档故障阻塞。

## 6. P3：补齐调度与日期覆盖

工作项：

1. 持续增量加入行数、字节和耗时预算，元数据缓存按 schema 版本失效；超大单行明确隔离/阻断，不跳过后标完整。
2. 新增近期回补与指定日期补齐任务，分别保存游标和重试状态；按 `(created_at,id)` 读取，不重置主增量游标。
3. 建立从可信覆盖起点开始的完整日期目录；今天、待核验历史、无数据候选、未知历史分别呈现。
4. 对缺失源索引、来源断档、源已清理、无效日期/未知收费类型建立明确错误/隔离状态。
5. 增量优先但为回补/核验预留有限预算，支持暂停、重启恢复、退避和按站点限并发。
6. 增加积压时间、读写字节、批次耗时、失败原因与日期缺口指标；默认值通过实测调整，不预先声称固定吞吐。

验收：迟到小 ID 被回补发现；零行日期与查询失败不同；补扫中断后恢复正确；当前日期与跨月时间边界不漏；未完成核验的日期始终不可用于正式出账。

## 7. P4：核验并发布不可变版本

2026-09-21 实现注记：P4a/P4b/P4c 已落地，Agent 升级到 019，CT 沿用 087。核验采用明确历史稳定/保留声明下的四轮独立分页扫描，不声称源快照；先修复再新运行核验。身份索引调整为按版本构建并通过 published JOIN 可见，以保持最后的目录发布为短事务。具体故障验证、生产边界与剩余工作见 [P4 操作说明](archive-p4-operations.md)及任务记录。

本批按三个可审查提交拆分，全部通过后才开放封存：

**P4a，持久化核验闭环。** 复用现有按日摘要，保存每次运行的源/目标范围、schema、行数、类型、quota/Token、字段摘要和保证条件。分块定位缺失/不同记录，补齐后复验；目标有而源无时保留证据，不自动删除对平。未证明源历史仍完整的日期保持 unknown。

**P4b，固定证据与事实。** 抽出共享字段提取模块并保留旧语义兼容分支。核验前记日 revision；核验后冻结日写入并复查 revision，不一致重跑。按内容摘要保存不可变计费原文，构建事实/异常/历史身份目录和必要汇总；building 版本不对账单可见。原文与事实构建可分批恢复，最终按行数/quota/摘要守恒检查。

**P4c，原子目录与修订。** 在目标同一短事务发布 manifest、日指针与 catalog_revision；跨日/月变更以一个修订批次整体发布。CT 丢失上报时可恢复目录，旧上报不得回退。冻结任务超时/重启由当前合法 epoch 接管；任何原始写入恢复后都使未发布的失效构建无法继续发布。

改动入口：`agent/internal/logarchive/reconcile.go`、新 evidence/facts/catalog 模块、共享提取包、控制回执与 CT 目录。

验收：核验与冻结之间写入、封存中崩溃、旧核验迟到、跨日改时间、schema 改动、旧 other 被镜像修正等场景均保持旧版可重放；日期摘要通过不掩盖 undated 收费异常。源读取一致性方法必须记录，不能把跨事务分页称为同一快照。

## 8. P5：自动采集并固定金额快照

2026-09-21 用户确认改为“自动读取并记录站点金额口径，出账时固定使用这份快照”，本批已实现。不建设人工金额配置中心、历史有效期时间线或额外结算倍率；本文其他章节中的历史配置覆盖设计以此调整为准。

1. 新建用户/上游对账单时，5 秒有界只读读取 new-api options，记录 QuotaPerUnit、显示币种/汇率、观察时间、白名单证据与计算口径标识。沿用现有适配器的内置 500000 默认值时明确标记来源。
2. CT 迁移 `088_billing_money_snapshots.sql` 建立不可变观察记录与任务绑定，两者与任务创建在同一事务提交。详情 JSON 返回 `money_snapshot`，不建立新的手工配置界面。
3. 计算、分页恢复、发布、失败任务重新创建均使用原绑定；源配置变化不重算旧账单。读取新配置失败/单位非法时拒绝新账单；已有绑定不再依赖在线 options 或当前余额发布。

5. 观察时间不代表历史生效时间，本批不承诺证明此前单位未发生变化。没有快照的旧未完成 statement 明确失败，需重新创建；已完成旧账单保持原文件。不改 legacy 日汇总任务的配置读取路径。

验收：精确小数、非法配置、站点隔离/校验和、源 options 不可用时计算与发布、失败重建不换快照、零输出过滤及 XLSX 金额通过；真实隔离 MySQL 验证迁移两次、事务绑定/回滚、复用和篡改拒绝。全量 Go vet/test 通过。P6 仍需绑定归档 dataset/generation/day_version，不能据此打开 archive_billing。

## 9. P6：完成归档账单的全部后端路径

**P6a，版本绑定 reader。** 新增 `OpenBillingSource(jobSnapshot)` 或等效接口；archive 与 legacy 按持久任务来源分派。按固定 catalog/day_version、用户及精确时间 keyset 读取，分页恢复不换版。用户/令牌选择来自历史目录，身份包含 generation。

**P6b，创建与保留引用。** 先在 CT 目录事务登记 preparing 任务/保留引用并阻止该数据集的清理，再在归档库一次一致性读取取得已发布、未标脏的完整版本集合；将其连同配置/算法上下文固化至 CT 后才允许入队。失败保留可恢复状态或显式取消释放引用，不依赖超时猜测可删除。

跨库不声称有原子事务：归档一致性读的时点是版本选择边界，读完后发生的修订不改变已选定输入，但需标明存在后续修订；已选集合必须来自同一 catalog_revision。目录在选择之前已脏或不完整就拒绝。运行前验证所引 manifest 仍可读，缺失/校验失败明确停下，不能重新绑定“最新”。清理只经统一 CT 互斥流程，一期不实现自动删除。

**P6c，确定的计算和重试。** 删除 archive 路径步骤中/发布时的线上 options、users、channels、余额读取；固定模型元数据及显示身份。保留既有消费类型、过滤和异常语义及版本，核对纳入/排除/隔离守恒。失败重试不删除 manifest 后重新选择来源；spool、compact、游标提交故障通过幂等恢复。

**P6d，修订与产物。** 业务查重与输入版本分开；新数据通过显式账单修订动作关联原账单，模板改变不绕过查重。保存计算快照、系统模板/渲染版本、完整文件清单与 hash；全部文件校验后发布，ZIP 缺成员必须报错。主表、每日、令牌、逐请求下载和关联核对都从同版读取，不跳往旧实时导出接口。

改动入口：`server/internal/billing/jobs.go`、`server/internal/mysqlstore/billing_statements.go`/`billing_jobs.go`、账单创建/结果/明细导出 handlers、Server runner 接线、新归档 reader。

验收：源库断开后历史用户选择→生成→计算/文件失败恢复→全部下载成功；同参数并发只创建一份业务账单；过滤、跨月、NULL、价格与多媒体样本逐条对齐；配置/日志/模板升级后原任务金额与已发布文件 hash 不变。

## 10. P7：页面和操作联动

页面规范见 [日志归档页面重设计](design-log-archive-page.md)，已提供独立交互原型供确认；原型验证不代替本阶段真实接口联调和权限验收。

1. 归档页拆成总览、每日数据、任务与策略；主指标为可出账覆盖和缺口，显示完整日期而非仅已上报日期。
2. 提供有服务端实现支撑的补齐、核验、失败重试、版本/差异查看；运行状态、日志完整性和账单就绪状态分开。
3. 用户账单选择归档历史用户，生成前展示范围检查与具体缺口；“已封存但金额口径待确认”单独提示。
4. 账单详情展示输入版本/金额来源/核验时间/修订关系；归档管理权限与账单权限分别校验，普通账单用户可看阻塞原因但不能借此操作归档。
5. 按已有站点切换、旧请求隔离、菜单显隐、管理员权限和手机布局规则实现；系统模板先上线，未实现的上传入口不假装可用。

改动入口：`LogArchiveView.vue`、用户账单/账单任务页面及相关客户端类型、权限和查询接口。归档接口可以先 mock 开发；用户可见操作必须等实际后端能力可用后开启。

验收：缺日不能绕过页面通过 API 出账；切站无串数据；零业务/未知历史文案清楚；桌面与 390px 手机、明暗主题、受限管理员实际交互通过。

## 11. P8：迁移演练和发布门槛

旧库导入工具应在 P1–P4 开发中形成，本批执行完整演练和灰度。以下顺序是未来上线操作清单，本次不操作生产。

1. **本地/测试环境演练**：备份恢复到隔离环境，核对旧库身份、schema、月表/贡献/统计、checkpoint 和源覆盖证据；演练新目标初始化与旧目标升级，不凭旧“已归档”生成封存版本。
2. **版本兼容验证**：新版 Server 支持旧数据集；旧 Agent不能领取新版任务；新版 Agent不能被旧 Server 授予新版任务；不兼容 reader/parser 明确拒绝新格式，未完成 legacy 任务保持旧来源。
3. **服务端准备**：先发布兼容 Server/控制接口及 CT 迁移；archive 新账单开关关闭。所有可能领取账单任务的 Server worker 都必须升级并停用旧进程后才能开启 archive 队列；只加 data_source 字段不能阻止旧领取 SQL 抢到新任务。准备归档只读连接和备份，不能让 Server 账单账号获得归档写权限。
4. **执行器切换**：暂停并停止旧归档进程，等待旧授权/事务结束，核实没有本地模式/旁路写入者；撤销旧写账号或换新版独立账号。安装新版 Agent但保持暂停，再执行归档目标预检、迁移、身份绑定和 checkpoint 接入。
5. **单站归档灰度**：小预算运行，完成增量、回补、逐日核验、事实封存、历史金额证据覆盖。保留未知日期，不因切换把它们标完整。
6. **影子比对**：同一稳定时间范围、同一输入配置分别运行线上/归档路径，比较行集合、NULL、quota、过滤、金额、用量、汇总和生成文件；不生成两份正式对客账单。
7. **断源与恢复验收**：仅在测试环境切断源连接，验证完整出账闭环；执行 Agent/Server 重启、提交响应丢失、文件缺失重试及一次备份恢复演练。
8. **负载门槛**：记录日志到达速率、归档处理速率、积压恢复时间、核验时长、源 CPU/IO/P95、Agent 内存、监控/告警延迟。目标阈值由 P0 基线确定，未达标继续调预算，不盲目扩大站点。
9. **切换与观察**：先为一个站点启用新用户账单 archive 来源，明确切换边界和历史缺口；至少完成一个完整归档日闭环及代表性跨月账单，再逐站扩大。发布记录只写实际结果。

回退：停止新 archive 任务和新归档写入，保留已封存数据/已生成文件；legacy 任务继续自身兼容路径。旧二进制不得重新接管新版目标或新格式任务，不通过改来源回线上继续同一账单。需要业务恢复时修复兼容版本后续跑，不能用数据库降级删除新证据。

## 12. P9：二期存储治理

待一期稳定且掌握实际增长后，单独实现保留策略、版本引用校验、压缩冷存、恢复流程及关联清理。先完成 dry-run 报告，再验证恢复，再开放可审计的清理入口。清理与入队/在途任务并发测试必须通过；不能只 DROP 月表。

未实现该阶段前，默认不自动删除原始归档、事实、计费证据或版本目录。源日志清理属于独立运维操作，不因本计划自动获得执行授权。

## 13. 每批交付与验证规则

- 每批交付代码、相应迁移/兼容说明、有区分力的测试和简短交接；阶段状态区分“代码完成、实库验证、页面验收、已发布、已部署”。
- Go 修改交付前执行根 Makefile 质量门：`go vet ./...`、`go test ./...`；Web 修改在 `webapp` 执行 `pnpm typecheck`、`pnpm build`。
- P1/P2/P4/P6 的迁移、锁、事务、跨进程故障不能只靠 mock，需真实测试 MySQL；未配置环境导致跳过时标待验证，不能跨过灰度门槛。
- P6 必须实际生成并检查工作簿、日附件、ZIP 清单、hash 与客户字段过滤；页面或接口返回 200 不等于文件完整。
- 所有检查写明运行版本和结果；本计划中的验收要求不是本次已通过的测试。
- 多会话可分别承担 Agent、金额配置和 Web；共享契约、迁移编号、`jobs.go`、当前总览由指定集成人员统一合并。不得多个会话同时重写同一文件。

建议开发交付分组：R1=P0–P3（可靠归档基础），R2=P4+P5（可封存并解释金额），R3=P6+P7（归档账单闭环），R4=P8（实测灰度），P9 独立后续迭代。R1/R2完成不代表已具备正式用户出账能力。
