状态：设计方案，尚未接入 CT 管理。当前本地归档代码及配置说明见 `newapi-log-archive.md`。本文不表示以下控制、限流和界面功能已经实现。

更新：月表、整体日/月统计、事务内差额去重和多行写入已在本地归档代码实现，详见部署说明。下面关于单表和逐行写入的旧描述已被替代；控制轮询、执行授权和低影响补扫仍待实现。

后续决定：按追加写请求日志处理，默认延迟 300 秒归档，已取消每日全表重扫，也不将历史修改同步作为需求。以下完整补扫设计暂不实施；源库时钟、批次边界等待及不越过未到期记录的游标处理已实现。

## 目标与边界

- 原始日志从源 RDS 经 Agent 到目标 RDS；CT 只传递配置和状态。部署时确认 Agent 到两个 RDS 的网络路径。
- 保留源日志；不修改源表、不增加源库写权限、不共享监控游标或报告缓存。
- 复用现有认证、权限、审计、HTTP 服务和前端组件；不增加消息队列、调度服务、Agent 入站端口或原始日志本地持久队列。
- 第一版数据库连接信息在 Agent 本地配置，CT 管理启停、批量、间隔和执行状态。目标连接变更需在 Agent 本地操作，避免本轮引入远程密钥管理。

## 已核对的代码与约束

1. `agent/internal/logarchive/archive.go` 已有独立连接池、事务写入、独立检查点、源目标身份和表结构检查。
2. `agent/cmd/control-tower-agent/archive.go` 当前启动后立即执行归档，使用固定 ticker；没有远程暂停、退避或执行租约。
3. `agent/cmd/control-tower-agent/main.go` 的 `collectAndReportFullPass` 先采集，再补传缓存，最后调用心跳。采集失败或补传失败会提前返回，不能将可靠的归档暂停完全依附于这条心跳路径。独立告警模式也不发 CT 心跳。
4. 项目已有 `/api/agent/container-logs/poll`，可参考其独立轮询、实例 Token 校验、Store 和 Dashboard Handler 接线方式，但不复用容器日志任务表或渠道命令类型。
5. 当前归档每批检查元数据、逐行执行 INSERT，首次追平后每 24 小时从头重扫。这些行为需要收敛后再作为低影响版本启用。

## 控制与状态

建议新增独立 `POST /api/agent/log-archive/poll`，约每 15 秒请求一次，HTTP 超时约 3 秒；控制 goroutine 与归档数据 goroutine 分离，不查询源 RDS。

Agent 上传：实例认证、Agent ID、启动会话 ID、能力版本、本地是否配置目标、已应用配置版本、运行状态、最后提交 ID、最近成功时间、本批行数/字节/耗时、累计处理行数、连续失败次数、简短错误码。累计行数包含补扫和重放，不能当作唯一归档行数。

CT 返回：递增配置版本、期望启停状态、批量、最小批次间隔、执行授权剩余时间。参数在批次边界应用；旧版本响应不能覆盖新版本。

- CT 保存期望状态和最新观察状态，归档实际游标以 Agent 的目标提交和本地检查点为准，CT 不能用监控 `last_log_id` 或展示状态推高归档游标。
- 页面暂停：CT 写入新版本 paused；Agent 收到后不启动新批次，当前批次提交并保存进度后确认 paused。收到确认前页面显示“暂停中”；超时显示“离线/等待确认”。
- 第一版配置绑定明确的执行 Agent。CT 按实例、Agent 和启动会话发放短期授权，例如 90 秒；同一任务只允许一个会话持有有效授权。过期授权加上批次超时的保护期后才允许交接，降低旧批次与新执行者重叠风险；不做自动跨机器故障切换。
- Agent 使用本地单调计时判断授权剩余时间，扣除控制请求耗时；只有剩余时间足够覆盖批次超时时才启动新批次。启动/重启先等待授权，不从本地旧 running 状态自动恢复。
- CT 断联不影响监控和告警；归档在授权到期后不再启动新批次。恢复连接后重新确认配置。暂停不是同步中断数据库事务。
- 旧 Agent 没有能力上报时，CT 显示“不支持，需升级”，不显示为已暂停或可执行。
- 云端托管模式显式启用，和原本本地模式互斥；不能在控制接口 404、鉴权失败或 CT 不可用时悄悄回退到本地自动归档。没有 CT URL/实例 Token 的独立告警模式不提供远程管理。

## 源库与资源开销

1. 使用主键范围分页 `WHERE id > ? ORDER BY id LIMIT ?`；部署预检确认源 `id` 为可用索引。不用 OFFSET，不做高频 COUNT，不扫描日志正文判断进度。
2. 保留默认 500 行/批、批后至少休息 30 秒作为初始配置，另设批次字节上限，例如 4 MiB。单条超限应报告并停在该记录之前，不能静默跳过；通过明确调整限额处理。默认上限约 1,000 行/分钟，执行耗时会进一步降低吞吐，必须对照实际日志增长率判断能否追平。
3. 固定 ticker 改成“本批结束后计时”，避免慢批次结束后马上消费积压 tick；启动加入小幅抖动，避免多个实例同时查库。
4. 源库和目标各最多 1 个归档连接，单任务串行；建议源查询超时 2 秒、批次总超时 15 秒，作为压测起点。先读完并关闭源查询，再开始目标事务，不因目标 RDS 变慢而长期占用源查询。
5. 写入失败和超时指数退避，例如 30、60、120 秒，最大 5 分钟，加抖动；暂停控制轮询保持正常。仅在目标事务成功后更新检查点。
6. 将目标逐行网络往返改为受行数、字节数和参数数上限约束的多行参数化 INSERT，保留事务及重放语义。不使用 INSERT IGNORE 掩盖截断或类型错误。
7. 表结构与目标身份检查在启动、连接目标变更、定期复核和相关写入错误后进行，不必每批完整查一遍元数据；保留严格 SQL 模式。检测源列变更或写入不兼容立即停止推进并报错，不自动 ALTER 表。
8. 进度页只展示已提交 ID、时间与速率；历史总量未知时不显示虚假的完成百分比。不为界面进度额外频繁扫描源表。

## 补扫与完整性取舍

不能简单删除每日全表补扫而继续承诺不漏日志：自增 ID 分配顺序不等于事务提交顺序。

建议第一版将每日自动全表重扫改为显式的低峰校验/补扫任务，并和正常增量分别保存进度，复用同一全局限流预算串行执行，避免补扫把增量游标退回零。周期和范围可配置，界面需展示最近完整校验时间。

对近期区间可做有界重叠补扫，降低正常运行成本；必须记录覆盖范围，并明确窗口以外的延迟提交和旧行修改依赖完整补扫才能发现。延迟归档或一个固定重叠窗口都不能数学上保证全量完整。源库继续保留数据，后续通过低峰核对和全量补扫修复；不在未验证完整性时增加源日志自动删除。

首次历史补齐也受相同限流与暂停控制；不会为了追平无限连续运行。若增长量超过归档能力，CT 提示积压趋势，由管理员调整预算或只读副本方案，不自动无上限加速。

## 最少接口与界面

- 一个增量迁移新增归档配置/状态表，按实例保存执行 Agent、配置版本、期望状态、最新观察状态、服务端接收时间及会话授权信息；状态数据有大小上限。
- `GET /api/dashboard/log-archives`：列表和状态。
- `PUT /api/dashboard/log-archives/{instance_id}`：版本校验后修改期望状态及限流参数，沿用操作审计，新增归档查看/管理权限。
- `POST /api/agent/log-archive/poll`：实例 Token 校验，Agent/会话匹配，上传状态并领取最新配置。
- 在实例管理附近增加归档面板：目标是否配置、执行 Agent、启停、批量和间隔、状态、最新成功时间、错误。先不引入通用任务编排器或凭据编辑器。

## 验收与发布顺序

1. 先完成 Agent 限流、补扫进度分离和故障隔离，再接入控制接口及 CT 面板；现有监控查询与上传合同保持不变。
2. 测试暂停发生在读、写、提交和保存进度阶段；只有批次结束并应用新版本后才能确认暂停。验证 CT 断联、Agent 重启、旧版本响应、租约过期和多 Agent 竞争。
3. 验证目标不可达、事务提交结果不确定、状态保存失败时可重放；NULL、长文本和数值精度保留；不删除或跳过源记录。
4. 用两笔事务复现“较小 ID 晚提交”，验证补扫能补回，并确保补扫不会推退正常增量进度。覆盖授权不足和超限单条日志。
5. 对照关闭/开启归档时的源查询耗时、数据库 CPU/IO、Agent 内存、监控周期和告警延迟，不只看功能测试通过。
6. 先发布 CT 的兼容增量接口，再升级单个 Agent；默认不运行，准备目标表后在 CT 小批量启用。灰度观察后再增加吞吐。回退时先暂停并等待确认；无法确认时停用 Agent 本地归档开关后再回退，监控继续运行。
