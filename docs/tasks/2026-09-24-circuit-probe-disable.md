# 熔断探针全失败后禁用渠道

## 行为

自动执行模式下，渠道熔断仍先置零权重并等待配置的静默期。完整一轮探针执行完毕，实际尝试次数达到该轮命令下发的次数且成功次数为零时，提交渠道自动禁用（status=3）及权重零的更新。部分成功、探针中断或没有结果不会触发这项禁用规则。

禁用成功后，继续按静默期调度下一轮探针。后续失败仍维持禁用；达到原有恢复评分条件后，提交启用（status=1）和软启动权重（默认基础权重20%，最低1）。成功确认后进入原有软启动和正常调权流程。

直连和Agent队列共用现有channel.update协议。队列路径等待执行回执，pending/delivered不视为成功，不重复投递；失败或过期允许重试，并沿用连续写入失败的退避机制。已投递命令结果未知时继续等待回执，避免重复启停命令乱序。

## 持久化与边界

- 新增迁移`093_tuning_circuit_disable.sql`，记录本流程禁用标记、待写状态和命令ID。状态意图先持久化，命令ID与命令记录同事务写入，支持Server重启接续。
- 调权候选查询保留本流程禁用的渠道，以便持续探测；其他已禁用渠道仍按原规则排除。
- 观察/关闭模式不执行新增启停操作。混合模型、基础权重为零等已有排除条件继续生效。
- 页面显示正在禁用/启用、等待执行确认、已禁用及下次检测，事件列表增加探针全失败禁用事件。
- 不新增探针接口，不需要新Agent协议；部署需升级Server并应用093迁移。未更改用户配置的静默时间、探针参数和恢复阈值。

## 再次复核与补修（2026-09-24）

发现并修正以下边界问题，范围仍限定在本需求：

1. 启用失败后原实现保留成功探针证据，可能在很久后直接重试启用。现改为回到静默/探测流程，重新满足恢复条件再启用；直连错误和Agent失败回执均覆盖。
2. 本流程禁用期间临时将基础权重设为零，原实现会清空熔断状态，恢复基础权重后无法继续探测。现对零基础权重和混合模型暂时排除保留恢复状态，也避免篡改待确认命令的目标权重。
3. 原实现只检查评估时的自动模式，排队后改成观察/关闭仍可能领取旧启停命令。现对新增的启停写入，在直连写入、入队及Agent领取时检查当前自动模式、归属/目标状态、基础权重和模型资格；已失效且尚未下发的命令过期，不执行。已下发命令无法撤回，继续等执行回执。
4. 探针期间修改次数会误判完整轮次。现读取已完成命令的原始probe_count，不新增数据库字段或策略参数；缺少原始命令证据时不据此禁用。
5. 为持续探测而纳入候选的禁用渠道，其旧统计原本会重新进入其他渠道的性能基线。现只保留恢复处理资格，不进入正常性能基线。

新增回归先复现启用证据过期、零权重清空状态两项问题再修正；状态机专项现有8项测试。Go全量测试和go vet通过，末次命令领取兼容处理后相关3包测试通过。MySQL用例扩充原始探针次数查询、模式变更取消领取，仍因缺少隔离数据库未实库执行。本轮未改前端，沿用上一轮前端验证，未发布或部署。

没有新增业务开关、通知、探测频率或恢复阈值。093迁移和执行回执是重启接续、状态准确性的必要支撑。Agent已投递命令回执长期缺失时仍保持等待确认，不把未知结果当失败重复发送；此边界尚未生产端到端验收。
