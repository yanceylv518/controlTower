# 上游管理审查与历史账单补漏方案（2026-10-10）

## 后续实施范围

用户随后确认先完善上游管理，遗漏渠道的上游账单暂用现有覆盖方式处理。当前实施及验证见[上游管理完善交接](2026-10-10-upstream-management-completion.md)：已修复管理、前缀迁移/确认、归属转移、关联来源、读取与同步分离、页面状态和覆盖月账发布保护。本文件以下保留审查时的事实与备选方案；定向补漏、差异预览及全日/月版本原子切换没有在本轮实现，不能当作已交付能力。

## 范围与业务前提

本轮审查当前工作区实现，包含此前未提交的多前缀、URL 记录、手动关联和折扣弹窗修改。用户明确：渠道不删除，上游通常长期保留；自动关联依据渠道前缀，手动关联允许不符合前缀。最新要求是提出“已生成账单遗漏渠道”的通用解决方案，不是核查某一份业务账单。

本轮没有提交账单生成任务、修改业务账单或修复产品代码。文中的方案均为待实施；本地演示环境验证不等于业务库或生产验收。

## 当前逻辑

1. 上游 ID 是稳定身份，显示名称与多个渠道前缀独立。新渠道按完整前缀名或“前缀_”匹配，最长前缀优先；未匹配时取首段自动建上游，默认关闭自动出账。
2. 已绑定渠道保持归属；人工移出记入排除表，人工加入不要求匹配前缀。当前没有自动/手动绑定来源和归属历史。
3. URL 从关联渠道自动收集，旧 URL 保留，手动补充为次要操作；URL 不再驱动归属，但仍沿用站点级唯一所有者限制。
4. 管理页读取及保存会先同步源渠道；新上游日账任务创建前也会同步。源渠道读取失败会阻断这些入口。
5. 日账创建时冻结渠道、模型范围及折扣快照；月账从已完成日账汇总。之后补充上游渠道，不会改变旧日账或旧月账。
6. 普通“补齐并生成”只补缺失日期，会复用已完成日账和已有无消费检查；“覆盖已有账单”重算整个上游的选定月份，重新获取当前保存的渠道、折扣和金额配置。

### 设计优化

- 保留既有归属稳定性；删改前缀默认只影响今后的自动发现，界面明确说明并给出匹配预览。不要因渠道改名或 URL 变化自动迁移旧归属。
- 记录关联来源、命中前缀、操作者和变更时间，人工移出的渠道可显式“恢复自动匹配”。人工归属允许不符合前缀。
- 渠道转移现在需两次保存，会短暂未分配，且折扣仍属于原上游。增加原子转移并明确折扣和历史账期归属；不能依靠删除上游纠错。
- URL 既已是资料，重新审视站点唯一所有者限制：共享地址会被静默跳过，手动转移后旧 URL 仍占用。至少区分当前使用、历史记录及冲突，不能展示成完整的当前地址清单。
- 管理页 GET 会写入及锁定整站上游，源故障又使本地配置无法查看。将同步与配置读取拆开，显示最近同步结果；源异常时仍可读本地配置，但不能把未知覆盖当作已完整出账。
- 前端还有“新增 URL 自动关联”“渠道冲突请核对 URL”的旧文案及无用 URL 匹配计算，应统一到前缀规则。
- 删除后自动重建不同 ID 已在隔离库复现；结合用户长期保留上游的场景，作为低频边界记录，不作为本轮主线。

## 已生成账单漏渠道：推荐方案

### 1. 保持旧账冻结，增加独立的“修复遗漏渠道”操作

新增渠道归属只影响后续任务，并标记可能受影响的历史账单。当前渠道集合与旧账快照不同只能说明需要检查，不能直接断言漏计：新渠道可能在该账期之后才有消费，也可能此前属于别的上游、已计入其他账单，或者被模型/零输出规则正常排除。

记录上游配置版本，日账保存实际渠道/模型集合及版本，月账沿用日账来源。可按指定账期执行只读检查，不在每次打开上游页面时扫描全部历史消费。

### 2. 修复前生成差异预览

预览包含：待补渠道、实际有消费的受影响日期、旧账是否已纳入、其他有效账单是否已计入、使用的折扣/币种/换算/零输出规则、历史明细是否完整可读。

归属错误已经在其他上游计费的情况，应同时修正两方账单，不能只给目标上游追加。无完整明细或无法还原历史计费口径的日期标为“待处理”，不能作为零消费通过。

### 3. 默认仅补遗漏，另设全面重算

- **补遗漏渠道**：保留原账已有渠道的正确结果与计费快照，只计算漏渠道在指定账期的消费，形成新的完整日账版本。漏渠道用该账期经确认的折扣及与原账兼容的金额口径，不直接套用今天的默认参数。相同渠道已有部分计费时须细分时间/模型或请求范围，避免重复追加。
- **按新规则重算**：用于用户明确需要修正原有渠道、折扣或币种等场景，重新计算全部指定范围，展示原有渠道金额也会变化。这与补遗漏的承诺不同。

两种方式都不直接改旧快照、不往已完成文件中拼渠道 ID，也不把一份独立补算结果直接加到旧月总额。已有渠道汇总可复用，但日账明细、各级汇总、导出文件和月账来源必须作为同一新版本一致发布。

### 4. 新版本全部成功后切换

冻结修复批次：旧版本 ID、指定渠道/日期、归属版本、折扣及金额快照、数据来源范围。生成替代日账，再组合未改日账生成完整月账；校验覆盖、金额与文件一致性，显示“原金额、补入金额、调整金额、新金额”。

只有全部受影响日期已完成或明确无消费、月账完整且差异核验通过，才在事务中切换当前月账及所引用的日账版本。修复过程中旧账继续可查看和下载；失败或取消保留旧账。重复提交/重试以修复批次和原版本为依据去重，并拒绝基于已被其他任务替换的旧版本再次发布。

保留旧版本及替代关系。若旧账已发送或结算，使用可追溯的更正版/差额单，并注明原账单，避免把新旧两版同时当作两笔应付。

### 5. 页面与实现顺序

账单详情或目录行增加“检查渠道完整性 / 修复遗漏渠道”，先展示差异，再提交修复；显示“修复中，当前账单仍为旧版本”，成功后展示补入渠道和差额。普通“补齐缺失日期”的名称应表达其真实作用。

实施顺序：

1. 修复现有覆盖生成提前废弃月账的问题，建立修复批次发布屏障。
2. 增加只读差异预览、历史口径及源数据完整性检查。
3. 实现定向补漏的新版本生成、去重、差异核验与日/月一致发布。
4. 补充配置变更提示及关联来源，减少后续漏项。

无需为渠道不删除、上游长期存在的业务额外引入频繁删除重建流程。

本轮代码审查覆盖上游配置、前缀同步、迁移、折扣页面、账单冻结、自动生成及月汇总。上游隔离 MySQL 探针 17.080s 通过，验证自动新建占前缀、删除重建和修改前缀后保留旧归属；探针及临时库已清理。现有上游/折扣18项前端回归通过；迟到折扣响应另用内存时序复现。

月账隔离实库探针16.881s通过（断言当前缺陷/行为）：旧月账覆盖30/30天，开启覆盖后没有任何新日账结果，仅尝试新建月账，返回no_data且旧月账变为superseded；另一完整月账仅发布1个替代日账，旧月账失效，新月账可发布为complete，但覆盖只有1/30天且覆盖完整性为false。后者是现有部分月汇总的有意行为（已有billing_partial_month_test.go覆盖），对历史完整账单修复仍需独立发布屏障。随机ct_review_month_*测试库与临时测试文件均已清理，无业务账单读取。
