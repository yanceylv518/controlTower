# 渠道延迟与多用户请求监控方案

> 2026-10-08后续讨论已收敛范围：第一版用现有request_length做系统请求大小趋势，暂不关联客户/IP；配套渠道延迟趋势和资源风险预警。完整现行设计见[请求压力与渠道延迟监控设计](../design-request-pressure-monitor.md)。下文保留早期讨论，不作为当前实施范围。

- 日期：2026-10-08，Asia/Shanghai。
- 用户目标：暂不探索内存/公网流出故障来源，新增快速定位高延迟渠道及多用户 IP、请求数、请求体大小监控。
- 状态：完成现有采集能力检查和方案草案；用户确认必须请求进行中可见、能看到卡住请求。未实现、测试、提交、发布或部署；入口类型与可用事件源待确认。

## 当前证据

- Agent logcollector 采集 NewAPI logs 的用户、渠道、模型、请求 ID、use_time，以及 other.frt；没有采集 IP 或请求体字节数。
- metricaggregator 已维护渠道和用户的 TTFT/总时长分布，可复用现有直方图。跨桶/跨实例汇总必须合并分布后计算分位数，不能平均各桶 P95。
- nginxtiming.ParseLine 当前解析 status/request_id/rt/uct/uht/urt/bytes，bytes 是响应体字节；没有解析客户端 IP 或 req_len。
- docs/latency-diagnosis.md 的 Nginx 示例含 remote_addr、req_len，但不能据此认定生产配置当前具有这些字段或已正确处理可信代理。
- req_len/request_length 包含请求行、请求头和请求体；Content-Length 是声明长度，可能缺失，不能无条件作为实际收到的请求体大小。
- Nginx access log 与 NewAPI 完成日志不能覆盖尚未结束的卡住请求；现有分钟桶关闭/上报机制不等于 5 秒实时。
- CT 是旁路系统。现有架构内可以做完成请求的近实时统计；在途监控和精确 body 字节需要业务侧或支持这些事件的网关提供元数据。当前未授权修改生产配置或 NewAPI 源码。

## 功能一：渠道延迟榜

- 按站点展示，默认窗口近 5 分钟，可选 1/15 分钟；按模型筛选，以免模型构成变化掩盖慢渠道。
- 建议默认按 TTFT P95 降序，允许切换总耗时排序。显示渠道名称/状态、TTFT P50/P95、总耗时 P95、请求数、有效 TTFT 样本数、超时数、最后数据时间。
- 慢阈值可配置；低样本标记、TTFT 缺失显示未知，不能补零。数据过期独立标记，不推断恢复。
- 若取得生命周期事件，增加在途数、尚未首响应数量、等待超过阈值数量及最长等待；单独展示在途异常，不能把正在等待的时长混入已完成 TTFT 分位数。
- 分离流式/非流式数据；首响应必须标明是响应头、首字节还是首 token，不能把 Nginx upstream_header_time 标作严格首 token 延迟。
- 点击渠道展开模型分布及慢请求元数据。不在本功能中自动修改权重或禁用渠道。

## 功能二：多用户请求监控

- 支持搜索、多选用户，同屏比较；用户汇总下展开 IP 明细，维度为站点 + 用户 ID + 规范化客户端 IP。
- 显示窗口内请求数、RPM、IP 数、请求体总字节/平均/最大/P95、字节速率、最近活动时间和数据覆盖率。
- 若取得生命周期事件，分开显示开始数/完成数、当前在途、最长等待；只有完成日志时明确显示完成请求数，不用它冒充实时到达数。
- IP 缺失、body 大小未知、用户归属待关联均单独计数。字节均值仅用有有效大小的请求作为分母；同时展示有效样本数。
- 主请求按稳定请求 ID 去重，上游 attempts 单独计数；一个用户请求 fallback 多次不重复累加用户入口请求体字节。
- 不同用户共用同一个 IP 不合并账号；同用户多个 IP 可展开；IPv4/IPv6 规范化。
- 仅使用配置的可信代理链解析真实 IP；不无条件信任客户端提供的 X-Forwarded-For。若只有代理 IP，页面明确标注来源。
- 只采集长度、标识和事件元数据，不采集请求体内容、Authorization、Cookie、API key 或带密钥的 URL 参数。

## 采集路径与实施顺序

1. 确认实时要求：完成后近实时，或请求进行中可见；确认 NewAPI/网关可提供的字段及关联请求 ID。
2. 渠道榜复用现有指标，新增短窗口查询与直方图汇总、覆盖率/新鲜度字段；保留现有渠道监控入口。
3. 用户字节/IP 采用独立元数据协议和 Agent 采集支路。优先复用已有可信数据源；Nginx 只提供 request_length 时展示“入口请求总大小”，不冒充精确 body 大小。
4. 精确 body 大小由读取请求体的业务/网关计数器提供，标明压缩传输字节和解压后字节口径；声明长度只能作为另一个有来源标记的字段。
5. 若需在途监控，源头提供 start/first_response/end/cancel 事件及用户/渠道关联；重新选择渠道时保存 attempt 归属。无事件来源时该项保持未具备，不能用前端刷新替代。
6. 独立有限批次上报，建议目标采集周期 5 秒、页面刷新 5 秒；端到端可见延迟由测量确认，不承诺两个周期之和之外无排队。隐藏页面停止刷新。
7. Agent 内存、关联等待队列、离线缓冲和用户/IP 高基数都有显式上限、过期规则及丢弃计数；结果批次幂等，异常不会阻塞现有采集。
8. 原始元数据短期保留、分钟聚合长期保留，具体天数按负载确定；查询分页、按站点隔离、适用权限控制，禁止无限拉取每个用户的所有 IP。

## 验证范围

- 分位数合并、低样本/缺失/过期数据、成功/错误/超时/流式口径。
- 批次重放、同请求多 attempts、多节点入口去重、延迟身份关联和无法关联数据。
- IP 可信代理、IPv6、多用户同 IP、body 声明长度缺失/不匹配、压缩与 chunked 数据。
- 生命周期乱序/重复/取消/失联清理，失联不能认定请求正常结束。
- 有限缓冲、高基数压力及源头不可用时现有采集继续工作。
- Web 多选、站点切换、分页、刷新取消和排序稳定性。
- 有源头测试数据后测量可见延迟；真实生产部署和验收独立记录。

## 待确认

- 渠道默认按首响应还是总耗时定位。
- Nginx/业务侧当前是否能提供可信 IP、稳定 request_id 和精确请求体大小。
- 已确认要求请求进行中可见；待确定业务入口类型及生命周期事件来源。
