用户要求：调权中心可手动禁用、启用渠道；手动禁用后不参与调权、不自动恢复；已启用、自动关闭及正在自动开启的渠道均可转为手动关闭。

## 页面行为

- 桌面渠道行和手机卡片将状态与操作合并：点击状态标签打开“修改渠道状态”弹框，选择“开启 / 手动关闭”后保存即执行，不再二次确认，也不再单独显示开启/关闭按钮。已启用渠道可手动关闭；自动关闭渠道既可开启，也可转为手动关闭。
- 弹框展示当前状态和目标状态的影响，操作作用于渠道所有模型。手动关闭后通过“手动关闭”筛选查看并开启，页面显示“未参与调权”，不再展示可执行的计算权重。
- 开启仅改变渠道启用状态，保留线上权重；之后按当前模型模式普通调权。线上权重为 0 时，开启本身不额外升权。
- NewAPI 侧开启与 CT 开启采用相同语义：CT 在渠道快照同步确认上游开启后解除手动接管，保留原模型模式和上游权重；可点击“刷新渠道信息”触发同步。
- 操作阻止重复提交；弹框取消不写入，未更改状态不重复保存，切站后清除编辑，失败保留弹框以便重试，权重/规则草稿保留。

## 后端保护

- 新接口 `PUT /api/dashboard/tuning/channels/{channelID}/status?site_id=...`，请求 `{status:1|2,confirm:true}`。沿用 `tuning.manage` 权限，校验站点与渠道归属。
- 使用现有 `tuning_continuous_states.paused_reason=manual_disabled` 持久保存手动接管，并推进 `control_revision`。写 NewAPI 之前先保存，清除旧熔断所有权、恢复命令标记、容量状态及评估快照。
- 普通调权、快速熔断、常态探针、恢复探针、性能基线和自动写入均排除手动接管渠道；旧评估和旧探针回执无法覆盖新状态。修改渠道模型列表也不能清除接管。
- 按站点/渠道使用 MySQL 会话锁串行化 CT 手动状态写入与自动权重/状态写入。如果自动开启已在途，手动关闭在其结束后执行；之后旧恢复请求因版本/所有权失效而停止。
- 锁定并失效旧的待执行自动命令及关联建议/审计；已有未确认的 Agent 写入或待执行人工队列写入返回 busy，避免旧命令晚到覆盖手动操作。
- 常态任务在下一次调度检查（现有 5 秒周期）取消；在途结果不能恢复或调权。恢复轮次在每次请求前后检查命令所有权，失效后不再发下一次。
- 上游失败、超时或结果记录失败保留手动接管；页面明确显示未确认，允许重试关闭或手动开启。CT 开启成功或新快照确认上游从关闭变为开启后解除接管，服务重启本身不会解除。
- 成功/失败通过现有命令审计和 CT 请求日志记录，渠道生命线显示“手动关闭渠道 / 手动开启渠道”，沿用现有记录保留配置。
- 本接口使用配置好的 CT 直连。无直连配置返回明确提示，不回落到 Agent 排队。

### NewAPI 开启同步补齐

用户进一步要求两处开启行为一致。原实现只撤销 CT 熔断所有权，未清除 `manual_disabled`，本轮已补齐：

- 成功手动关闭记录确认时间；后续更新的开启快照可解除手动接管，即使渠道目录曾重建或切换采集节点。
- 关闭请求未确认时，必须另有实际观察到的关闭 → 开启转换；仅连续收到原来的“已开启”状态不能推断发生了新的开启操作。
- 当前手动写请求仍在途时不解除接管；旧快照继续由采集时间保护拦截。
- 解除时推进控制版本、清理旧恢复/容量/探针证据，避免旧评估回写；重复开启快照不重复重置调权。同步过程不额外写入 NewAPI、不修改自动/观察/关闭模式，也不发起软启动。
