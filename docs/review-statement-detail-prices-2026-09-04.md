# 验收记录：对账单日统计单价改用明细快照价（2026-09-04）

- 范围：`2b67b4d fix(billing): use detail snapshot prices in statement summaries`
- 结论：**通过，验收修正三处 P2**（同一文件内，附回归测试）。解析成本与
  根治方向记档。

## 变更

- 对账单预览与导出工作簿的"日账单统计"四个单价列，原先查 CT 计价表按模型
  和日期选价（配置价，与金额无关，未配价即为空）。现改为解析该对账单登记的
  每日明细 xlsx，回收逐笔请求实际使用的单价，按（日、模型[、渠道]）汇总。
- 请求明细在任务完成时会从库中删除，明细文件是唯一留存的逐笔单价来源；
  解析文件的做法让已生成的旧对账单无需重生成即可受益。
- 单价缺失时显示"明细价格不可用"，工作簿里非数字单价以文本单元格输出。
- 移除 `ListBillingPrices` 依赖与 `statementPrice`。

## 缺陷与修正

**① 单价按整元组拼接，常态下重复且混入零价（P2）**。同一天同模型的请求
只要有的命中缓存、有的没有，或有的零输出，单价元组就不同；原实现逐列把每个
元组的值都拼上，实证得到 `input="1.000000 / 1.000000 / 1.000000"`、
`cache="0.000000 / 0.000000 / 0.100000"`。明细文件对未使用的泳道写的是数字
0，不是空。修正：按列去重；某列存在正价时丢弃 0（未使用泳道的 0 不是价格），
全零才显示 0；按数值排序。回归 `TestStatementPricesDedupePerColumn`。

**② 按文件缓存上限 128 条、超限整体清空（P2）**。上游对账单按用户按日登记
文件，一个月几百个文件很常见，缓存永远装不下整份对账单，每次预览全量重解析。
修正：已完成的对账单不可变，改为按对账单整体缓存（键=任务 + 全部文件的
路径/大小/mtime 签名），上限 32 份；多文件并行解析（4 路）缩短首屏。
回归 `TestStatementPricesCachePerStatement`（含坏文件必须报错而非静默丢价）。

**③ 依赖登记表 bill_day 做键，rc83 之前登记的文件全部对不上（P2）**。
f7a8fa4（2026-08-31）之前 spool 路径把账单日构造成上海零点，驱动按 UTC
落 DATE 列退一天（烟测库现存对账单即如此：登记 08-19，账单行 08-20）。
新功能对这类对账单整份显示"明细价格不可用"。修正：明细工作簿第 2 行自带
"账单日期"，解析时读出并优先作键，登记值仅作回退。
回归 `TestStatementPricesUseDeclaredBillDay`。

## 记档（P3，不阻塞）

- **解析成本**：encoding/xml 解析 20 万行明细约 21 秒，纯 tokenization 就要
  11 秒，手写解析最多快一倍，解决不了。每用户每日文件通常不大，并行后可接受；
  上游对账单跨全部用户时首屏仍可能数十秒。根治应在生成期把每日/模型/渠道的
  单价集合落库，文件解析只作旧对账单回退——属新批次，未动。
- 按次计费模型的行，Token 单价列在明细里是 0，日统计显示 0；按次单价本身
  日统计没有列。
- 混合零价与正价的判定：若同一天同模型确有免费改收费的价格切换，零价会被
  正价挤掉；极罕见，记档。
- 下载包内每日明细的文件名仍取登记表 bill_day（本例为 08-19），与日统计行
  引用的 08-20 不一致——rc83 前登记的旧数据症状，重生成自愈，非本批范围。
