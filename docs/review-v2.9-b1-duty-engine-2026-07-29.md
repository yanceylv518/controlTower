## 验收修正（两处存储层 SQL，假 store 测试无法暴露，生产必然空转）

1. **QueryMetrics `CAST(dimension_key AS SIGNED)`（v2.1-B1 遗留）**：instance_channel 的 dimension_key 是 `<实例>:channel:<id>`，整串 CAST 恒为 0 → 引擎永远匹配不到任何渠道指标。**这意味着旧 observe 引擎自 v2.1-B1 上线以来在生产从未产出过有效建议**（无人消费故未暴露）；值班引擎全依赖此查询。修复：`SUBSTRING_INDEX(dimension_key,':',-1)` 取尾段。
2. **QueryP95Buckets `dimension_key=?` 直接绑数字 ID（本批新增）**：永匹配不到 → 延迟基线永空 → 延迟判定静默失效。修复：`CONCAT(?,':channel:',?)` 构造完整 key。

两处均补 SQL 契约测试防回归（tuning_test.go）。

- observe 模式下"假设换班"后备胎并未真实接流量，备胎评估多为样本不足跳过——observe 固有局限，命中率信号以"原在岗者持续劣化"为主，合理。
- 评估节奏=每窗口（15 分钟）一轮（Tick 每分钟只做回填与到期检查），与设计实例时间线一致。
