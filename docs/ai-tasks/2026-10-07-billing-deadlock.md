# CT 旧月账单替换死锁修复

- 标识：2026-10-07-billing-deadlock
- 更新时间：2026-10-07（Asia/Shanghai）
- 状态：本地修复与验证完成，待发布/生产验收
- 目标与验收条件：缩小旧账单替换锁范围，补齐月账单创建的站点互斥，事务有界重试；保留旧账单及日转月金额。
- 负责会话、分支和范围：当前会话，main；仅 Server mysqlstore、回归测试及相关文档。保留 AGENTS、调权测试、其他任务/发布文档等原有未提交修改。

## 证据与设计

用户提供 MySQL 死锁截图：2026-10-07 01:44:19，control_tower.billing_jobs，pinducloud-cn，用户 2/26 的旧月账单关联 UPDATE 相互等待站点索引和 PRIMARY 锁，事务 1 回滚。不能认定与用户 25 在北京时间 09:37:36 的失败是同一次。源库日志不参与这份死锁。

1. supersedeBillingStatement 的两条宽范围关联 UPDATE 改为普通查询目标 ID，按 ID 顺序逐主键更新，强制 PRIMARY 访问并重新检查站点/对象/账期/状态及日月来源条件。新账单发布和旧账单替换仍在同一事务，失败回滚保留旧账单。
2. 更正之前咨询中的宽泛描述：有数据月账单早已排队，由 CompleteBillingMonth 在站点租约下发布；无数据月账单在创建入口直接替换旧结果。本次在所有 v3 月账单创建事务开始前，用同一专用连接非阻塞获取共享站点锁，既覆盖无数据分支，也使日来源读取的事务视图在租约内建立。忙碌返回现有 ErrStatementQueueFull，由自动补齐后续重试；不用持锁等待生成结束。不同站点的执行锁独立。原有全局短期入队锁仍保留。
3. CreateBillingStatementJob、CompleteBillingMonth、FinalizeBillingJob 增加完整事务重试：仅 MySQL 1213，最多三次尝试（含首次），退避 50/100ms，支持 context 取消。不重试 1205、业务错误或结果不确定的连接/提交错误。保持原任务级重试，不修改计费、文件导出或源库访问。
4. 不增加数据库迁移、不改 Web 或 Agent，不通过调大超时处理此问题。
