## 发现与影响

| 优先级 | 项目 | 结论与定位 |
| --- | --- | --- |
| P1 | P95耗时 | 线上已出现P95>P99。mysqlstore/latency_histogram.go的latencyP95MergeSQL将合批P95写成旧V1桶上界；store.go合批清空P50/P99却保留这个P95；metrics.go读取时优先非空存储值，P99则用V2插值，来源混用。overview.go又在多实例时取最大P95而非合并分布。不能把120.00s当作精确全站P95。修复需顾及已有存储行及直方图尾桶是下界而非有界区间。 |
| P1 | 当前告警 | 36小时48分旧记录仍以当前告警展示。API在mux中关闭请求时生成，读取持久告警；后台runner负责更新/消解。页面不展示时间与更新健康，读取成功不能证明评估仍正常。具体后台停更原因需生产日志/worker状态，当前未核实，不能直接归因磁盘故障。 |
| P2 | TPM/请求数/成功错误率 | 当前未结束分钟参与展示，没有“本分钟累计”或明确区间；短时间会明显增长，下分钟回落。latestMetrics查询24小时内各实例最后一个桶，总览不校验时效或统一bucket_time，可能把旧分钟/不同分钟混加。成功/错误率只对consume/error日志口径有效，不是ALB入口请求成功率，也不是渠道健康率。 |
| P2 | 近一小时趋势 | OverviewView.vue只取latest.items[0]，请求这一实例历史，却标题称全站。当前只有一份采集指标，未证实此站点当下少算；多个独立采集源时必然漏显示其余来源。还包含当前未完成分钟，缺口无固定时间轴补空，曲线可能跨缺口连线。 |
| P2 | 平均耗时 | 当前值未证明错误；是日志use_time，非首Token耗时。跨实例时用全部请求数作分母，即使某实例avg缺失也计入，可能被压低；合法全零耗时返回null。需注明耗时口径并按有效样本处理。 |
| P2 | 健康检查/容器 | 健康是本机状态接口连通，不是渠道探针。查询先取所有实例最新200条历史、再按站点过滤及对象去重，可能漏掉慢上报对象；无过期判定。容器无记录被显示成0且绿色，应显示未上报/未采集，缺数据不能当健康。 |
| P2 | 切站/并发刷新 | refresh缺少请求序号、取消或防重叠，await期间继续使用可变site_id，旧响应可能覆盖新站点或将卡片和曲线混在不同站点；现场首刷观察到两套相同请求。 |
| P2 | 刷新失败/最后刷新 | 三接口Promise.all互相牵连；卡片赋值后再取history，会出现卡片更新而曲线保旧；后台失败静默，旧数据没有显著过期提示。“最后刷新”是浏览器请求完成时间，不是指标采样时间。 |
| P2 | 告警范围 | 先取所有站点最多50条，再在前端按本站过滤至5条，其他站点可挤掉本站告警；active_only还包含未解决状态，不能据此推断刚刚产生。 |
