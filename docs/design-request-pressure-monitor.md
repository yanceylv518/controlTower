## 1. 目标与范围

### 最新评审方向：分档请求数曲线与重点渠道（2026-10-08）

用户明确选择“各大小档位的请求数随时间变化”，同时调整渠道范围为“只加载当前请求量大、延迟比较高的几条”。此前全渠道常驻列表及请求大小热图由本轮方向取代，CPU/内存主趋势保留；整体仍为设计评审，未授权实施业务功能。

- 用户最新明确“小于5 MiB作为一个档位”，取代上一轮排除小请求的理解。请求区统一四条折线：`<5 MiB`、`5≤大小<10 MiB`、`10≤大小<20 MiB`、`≥20 MiB`；横轴时间、纵轴每分钟请求数。Agent聚合/上报四档，<5 MiB仅合并为一档，不恢复100 KiB/1 MiB等细分。MiB按1024² byte计算。
- 汇总分别显示“四档合计”和“≥5 MiB合计”，后者等于后三档之和；图例隐藏不改变任一合计。页面保留数量趋势，无需恢复全档/大请求切换或占比模式。现有独立业务请求监控、渠道请求量筛选沿用原口径。
- 完整覆盖且某档无请求的窗口为0，缺失窗口断线；大小未知的记录不归入任何一档，单独报告unknown_size_count，四档合计明确仅包含已知大小记录。
- 渠道默认最多5条，必须同时满足近5分钟请求量门槛、首响应P95门槛、有效样本与数据新鲜度条件；默认按请求量降序，P95次序，ID作稳定兜底，也可选择延迟优先。预览使用≥100次/5分钟且P95≥10秒，均为未按生产容量校准的示例，不视作用户确认的生产阈值。
- Server先筛选当前候选，仅返回入选渠道的趋势及必要摘要；不可向前端加载全部渠道历史再截断。请求量用渠道已完成请求总数，首响应有效样本另计，至少20个；近5分钟P95由原始分布/可合并直方图计算，不能平均分钟P95。具体字段映射在实施时核实。
- 本轮模拟场景仅3条符合条件，展示3条，不凑满5条。没有符合条件的渠道显示空状态，数据未知的渠道不能据此被认定健康；采集异常通过摘要提示，可进入既有诊断页核对。
- 当前渠道名单及近5分钟摘要按最新窗口筛选；拖动历史时间仅联动曲线和单独的历史读数，不重写“当前”摘要，也不让名单随鼠标重排。源窗口更新可重新筛选，变化需清楚提示。

### 上一轮候选：CPU/内存风险与多渠道对照（2026-10-08）

用户明确否定弱化其他渠道的简化设计，并要求关注 CPU 何时暴增、内存何时暴增。前述三层简化预览未获确认。最新候选先展示每个节点 CPU/内存趋势，再展示全部渠道独立趋势（示例 12 个，统一时间和延迟纵轴），最后对照全站请求大小分布。渠道逐行显示选定窗口的 P95、有效样本和状态，支持慢渠道优先、异常筛选和最多 4 渠道放大对比；低样本、采集缺口独立显示。示例仅同模型比较，不能把全站请求大小关联到某个渠道或断言其导致节点资源升高。

本次候选为模拟数据。浏览器验证了 12 渠道同时展示、3/4 渠道对比及选择上限、5 个异常/未知渠道筛选、时间联动、资源读数、排序和口径展开；1024/736/540/390/320 视口无横向溢出、无脚本错误。仅验证交互设计，未实现业务采集、测试业务链路、提交、发布或部署。布局及新增采集范围仍待用户确定。

监控区分以下风险模式，均为待验证假设而非故障归因：

| 同期现象 | CPU 风险 | 内存风险 | 需要的证据 |
| --- | --- | --- | --- |
| 请求量陡增、单请求大小稳定 | 单位时间解析/转发等工作增多，可能升高 | 并发也增加时可能升高 | 资源采样、请求计数；完成日志不当入口到达量 |
| 大请求占比/字节处理量陡增 | 若业务解析、复制、转换或解压，计算与分配成本可能升高 | 同时保留的数据可能增多 | 大小分布、进程 CPU/RSS，后续分配率/堆证据 |
| 多渠道变慢、新请求持续进入 | 等待网络本身不意味着 CPU 必然高 | 已接收请求和缓冲保留更久，可能累积 | 渠道延迟、内存变化；精确在途仍需生命周期事件 |
| 超时重试放大 | 重复处理增加，可能升高 | 重试保留数据或并发放大时可能升高 | 实际 attempt/重试计数；当前不能拿普通请求数代替 |
| 分配率高、GC 更频繁 | GC CPU 开销可能增加 | 可能出现锯齿波或持续高水位 | NewAPI 自身 GC/heap 指标或受控性能采样，现未接入 |
| 请求/渠道已回落，内存仍持续增加 | 不确定 | 缓存增长、长期引用、后台任务等均需排查，不能直接判泄漏 | 进程/容器内存、堆存活量及足够长的观察窗口 |
| 资源升高但请求指标基本不变 | 可能是其他进程/后台工作 | 同样需要区分占用主体 | 主机与进程/容器双层证据 |

内存风险的直观依据是“同时存活的请求数 × 每请求保留的数据”，但这不是内存计量公式。缓冲、复制、堆/栈、缓存、页缓存及临时文件会改变实际占用；`request_length` 之和不能当作内存字节。Nginx 大请求可以写入临时文件，不能推断全部常驻内存。

页面首先回答“哪个节点、何时、升高多少”，随后提供同时间窗的请求和渠道证据；不能仅从相关性自动填写根因。主机异常检测可用现有资源采集扩展，确定 NewAPI 占用需另补进程/容器指标；运行时 GC/堆和精确在途属于额外接入能力。

目标是让运维尽早发现“大请求增多、渠道变慢、节点资源持续上涨”的风险，并能从同一时间轴判断何时应切换渠道或收紧入口并发。

本轮按最新讨论收敛为两项主功能：

1. 系统请求大小四档数量趋势与大请求字节负载辅助监控，不依赖客户/IP关联；小于5 MiB合并为一个档位。
2. 多渠道延迟趋势与慢渠道定位，辅以节点资源和风险通知。

用户已接受第一版采用 Nginx `request_length`，页面称“请求大小”，旁注“含请求行、请求头和请求体”。页面以趋势图为主体，排行和样本作为下钻辅助。

第一版在 CT Agent、Server、Web 内实现；使用现有访问日志和 NewAPI 指标。业务请求中的精确在途监控仍是目标，但现有数据不具备，列为独立后续阶段，不以完成日志冒充实现。客户关联、客户真实 IP、精确纯请求体计数、自动限流、自动重启或清队列不作为第一版依赖。

## 3. 统计口径

| 名称 | 定义 | 限制 |
| --- | --- | --- |
| 四档合计 | 单一权威访问日志内、属于监控接口且大小合法的四档记录数之和 | 缺大小不归档，显示覆盖率；不是实时到达数 |
| 大请求总数 | 单一权威访问日志内、属于监控接口且request_length≥5 MiB的有效记录数 | 三档之和；包含命中阈值的成功、失败、中断；不是实时到达数 |
| 请求大小 | 记录中的 request_length/req_len，单位 byte | 包含请求行、头、体；中断/拒绝可能只接收一部分 |
| 大请求平均大小 | 命中三档的字节总和 / 大请求总数 | 辅助统计；不代表全部请求平均大小 |
| 大请求最大大小 | 窗口内命中三档的最大request_length | 无命中时为无样本，不能代表计划上传大小 |
| 大请求 | request_length ≥ 5 MiB（5,242,880 byte） | 后三档归为大请求，<5 MiB为独立合并档 |
| 大请求字节量速率 | 按完成时间归桶的三档字节总和 / 桶秒数 | 页面提示“按请求结束时间统计”；不是实时网卡带宽 |
| 渠道首响应 | NewAPI 已有 frt 指标，沿用现有单位和有效性判断 | 首版为已有流式有效样本；缺失不拿 Nginx uht 替代 |
| Nginx uht | Nginx 等待 NewAPI 响应头的耗时 | 不是严格首 token 时延，也不是模型上游单独耗时 |
| 渠道总耗时 | 沿用 use_time 口径 | 长输出、重试都会影响，单凭它不判渠道首响应故障 |
| 节点内存 | (MemTotal-MemAvailable)/MemTotal | 主机压力，不等于 NewAPI 进程内存 |
| 节点 CPU | 有效采样间隔的主机 CPU 时间差分 | 标注整机 0—100%；不与单核/进程超过100%的口径混用，不代表 NewAPI 占用 |
| 网卡发送速率 | 指定接口字节计数差 / 有效采样间隔 | 公私网可能混合；不是云账单公网流量 |

### 3.1 时间口径必须固定

- Nginx 按日志记录的请求结束时间归桶，保留 occurred_at、collected_at、received_at 三类时间。
- 例如一个 40 MiB 请求在 14:00 上传、14:02 结束，其字节会出现在 14:02 的访问日志统计中；不能将其称为 14:02 的实时上传突增。
- NewAPI 渠道指标暂沿用已有源时间归桶；上线前用固定样本核验 created_at 语义。即使它代表开始时间，数据仍需结束落库后才能获得。
- 不从 rt 倒推并实时补造开始事件；不由完成率下降直接推算在途数量。
- 所有存储 UTC、前端按站点/现有时区展示，默认 Asia/Shanghai；客户端时间不参与服务端告警。
- 时钟异常、无合法时间、未来时间超过容差的记录不得替换为当前时间产生假峰值，应计解析异常；建议时钟容差 5 秒。

### 3.2 请求大小分档

统计四档：`[0,5) MiB`、`[5,10) MiB`、`[10,20) MiB`、`[20,+∞) MiB`。小于5 MiB整体计入第一档，不进一步细分。

每档保存请求数和字节和，页面展示四条数量折线；后三档字节用于大请求负载预警。MiB按1024² byte，字节聚合用整数。四档合计与大请求合计明确区分；无需新增更细的大小分布或占比模式。

本轮不采集请求大小P50/P95细粒度直方图。渠道首响应/耗时的既有直方图及合并分位统计继续按原口径工作，不能与请求大小分档混淆。

- 渠道按最新近5分钟请求量与延迟双门槛筛选，Server最多返回5条趋势；默认请求量优先，最多4条放大对比。回看历史时名单保持稳定，新来源窗口触发名单变化需提示。
- 渠道辅助列表支持首响应 P95/总耗时 P95 排序，显示样本数、更新时间；大图可切换首响应/总耗时，同一坐标轴只放同一种单位。
- 渠道可按模型筛选；该筛选只作用于渠道面板。请求大小图没有模型维度时不跟随，避免显示范围错配。
- 节点选择影响节点流量与资源；若渠道日志来自共享数据库，则渠道保持站点口径，面板明确“站点渠道”，不能声称是所选节点的渠道耗时。
- 事件标记可点击，显示触发证据和建议，再跳既有调权/系统状态页面操作。
- 隐藏标签页停止轮询；离开页取消请求；合并同参数在途查询；切站点清除旧响应及旧选择。
- 不设无效“实时”绿点；显示各数据源最后采集时间、滞后秒数、覆盖节点 x/y。

### 4.3 空值和异常状态

- 无大请求且采集覆盖完整：大请求数量/字节为0，最大值为“无样本”；渠道无有效首响应样本则渠道P95为“无样本”。
- Agent 失联、源文件不可读、解析失败或积压未读完：曲线断点/缺失区间，不补零、不判恢复。
- 单节点缺失：全站曲线虚线或缺口标识、展示 x/y 覆盖，不能给完整站点“正常”结论。
- 当前未结束桶浅色标识“统计中”；报警只用满足完整窗口的最终值。
- 已有错误或高压告警遇到数据失联，状态改“待确认/数据中断”，不能自动关闭。

## 5. 数据采集与传输

### 5.1 请求流量来源

首版优先复用 `/var/log/nginx/newapi-timing.log`：现有路径及权限链路已具备基础，只补 req_len 解析和独立聚合。支持 JSON 适配作为另一个可选来源，同一逻辑入口只能启用一个统计来源。

每个源登记 source_id、实例、站点、路径、格式、generation、接口白名单和生效时间。timed 无 host，必须确认该文件属于单一站点；共享日志有多域名时改用 JSON 的 host 过滤，不能靠请求 ID 猜站点。

只统计配置的业务 API（首批 `/v1/chat/completions`、`/v1/responses`、`/v1/messages`，实际路由清单接入时核对），路径归类为有限枚举；不把管理接口、健康检查和静态文件混入。不要擅自把所有 `/v1/*` 归为推理请求。查询字符串在解析时剥离。

Agent 在每个实际承载入口流量的节点读取本机日志。NewAPI 共享数据库只由既有业务采集 Agent 读取；不能为了流量监控把所有节点的源库采集都打开。

### 5.2 聚合与幂等（采用增量批次）

- 将大小合法的记录按10秒结束时间桶、source_id、接口族、状态类别聚合；保存四档数量/字节、known_size_request_count、large_request_count及大请求字节和/最大值等摘要。显式携带边界[0,5242880,10485760,20971520]、large_request_min_bytes=5242880及统计版本；<5 MiB整体累加第一档，空窗口覆盖由独立健康水位证明。
- 每 5 秒将新增的桶增量形成不可变 batch，先落本地有界持久日志，再推进对应文件游标；batch_id 包含持久 collector_epoch + 单调序号。
- cursor 与聚合增量属于同一个可恢复提交单元。崩溃重读由 WAL 恢复/提交标记消除重复，不依赖时间或 request_id 去重。
- Server在一个事务内插入批次身份并更新聚合，已处理batch返回成功但不重复累计；四档计数/字节分别求和，max求最大。
- ACK 之后才能清理已确认 WAL。请求 ID 可能为空、重复或对应客户端重试，不作为接入层请求唯一键。
- 同一入口不同日志重复、同一物理节点多个 Agent 重复的问题用来源登记与单写者租约预防；只接受当前有效 source writer epoch，同一源不能同时归两个 Agent。
- 多个真实入口请求即使 request_id 相同也分别计数，它们确实产生了入口流量；未来客户关联另有逻辑请求口径。
- 自动历史重放只恢复有断点的未确认批次；首次启用从尾部开始，显示 coverage_start。历史回填另设显式任务，本轮不混入实时告警。

### 5.3 文件处理和数据质量

- 处理半行、轮转 rename/create、短时不存在、权限失败；旧文件读至 EOF 后切换新文件。
- file identity + generation + byte offset 持久化；copytruncate 导致无法保证完整时明确记录 gap，不声称零丢失。
- 单行最多 64 KiB，超长行流式丢弃至换行，不先分配整行；数值只接受非负有限值并做溢出检查。
- status/时间/大小各自记录解析结果；大小缺失计入unknown_size_count，不归入四档或大请求总数，并降低覆盖率。小于5 MiB的有效记录进入第一档；合法0 byte与字段缺失明确区分。
- 采集状态独立定期上报：poll_at、read_through、last_event_at、readable、parse_error_count、unknown_size_count、dropped_count、file_lag_bytes、clock_skew、coverage_start。
- 无请求不能通过 last_event_at 判断 Agent 失联；用 poll/read_through 证明完整空窗口。
- 413 计数来自访问日志；错误日志的 too-large-body 仅作为可选示例事件/计划大小补充，不再增加请求数和字节总量。无精确关联时标“独立错误样本”。

### 5.4 资源与可选 Nginx 状态

- 资源建议每 5 秒独立采样、批量上报；只安排一个采样器，主报告复用最近值，不重复执行网络差分采样。
- CPU 增加当前值、窗口最大值、有效采样覆盖及采样间隔；按节点展示，不以多机平均掩盖热点。后续按需求分离 user/system/iowait/steal、最忙核心与容器配额限速，先校验 `/proc/stat` 字段含义及 guest 时间不能重复计入。平均与最大值分开保存；5秒采样仍不能保证捕获更短尖峰。
- 若需回答“是否为 NewAPI 导致”，另补稳定进程/容器身份下的 CPU、RSS/容器内存及限制，避免 PID 复用、跨容器归属错误。Go 的 heap、分配率、GC CPU/次数需 NewAPI 自身可用的运行时出口，CT Agent 自己的 GC 指标不能代替。采不到显示未接入，不显示0。
- 新数据增加 valid/available 字段；读取失败、计数器重置、首次无前值显示未知。旧 Agent 无有效性字段不用于新增增长率/带宽告警，已有历史继续可读。
- 网络新增接口选择，默认需要明确选择物理/业务接口；记录接口名和方向。不能将现有“所有非 lo 网卡合计”用作指定出口占用率。
- 内存补 MemTotal/MemAvailable byte 以便查看余量，增长率使用最近 3 分钟有效样本的稳健斜率，单位“百分点/分钟”；至少 80% 覆盖且最大连续缺口≤15秒，重启后重新收集窗口。
- 可选每 5 秒只读请求本机 `/nginx_status`（超时 1 秒），采集 requests 差分和 Reading/Writing/Waiting。接口保持本机可见，不开放公网。
- stub_status 是 Nginx 进程级数据，可能含其他站点；与 API access_log 口径不同，不相减计算在途数。Waiting 是空闲 keepalive，Writing 也不能等同上游排队，HTTP/2 连接数更不能等同请求数。
- 首版将这些连接趋势作为辅助；没有专属来源和验证前不驱动积压组合告警。

### 5.5 时效目标

| 链路 | 设计值/验收目标 |
| --- | --- |
| Nginx 新日志读取 | 1秒内发现可读追加；日志自身缓冲另计 |
| Agent 报告 | 每5秒；独立于源库查询和归档任务 |
| 底层桶 | 10秒，允许当前桶部分值展示 |
| 页面刷新 | 5秒，仅可见页 |
| 请求结束至首屏可见 | 正常链路P95≤15秒，实际压测确认 |
| 10秒完整桶可用 | 正常链路目标≤20秒（含封桶余量及报告） |
| 渠道新指标 | 沿用现有采集与分钟聚合，显示实际滞后；初始验收目标≤90秒，先实测 |
| 资源变化至首屏 | 正常链路P95≤15秒 |

以上不包含请求执行时长。一个卡住 120 秒的请求不能因为 5 秒轮询而在开始后 15 秒出现在大小图上。停止到达的日志不意味着系统空闲。

## 6. 预警规则

规则以站点为配置单位，实例资源规则按节点评估。以下为可编辑的初始建议值，不是已验证的 pinducloud 承载容量。先观察校准，再启用外部通知。

### 6.1 规则表

| 规则 | 触发建议 | 持续要求 | 严重性 |
| --- | --- | --- | --- |
| 大请求负载上升 | 滚动60秒三档字节速率≥配置绝对门槛且≥基线2倍；有效大请求样本≥20 | 持续60秒、随新数据推进 | 预警 |
| 渠道首响应偏高 | 最近5分钟TTFT P95≥站点阈值（建议初值10秒）且有效样本≥20 | 两个不同分钟截止点满足 | 预警 |
| 渠道首响应严重偏高 | 同口径P95≥严重阈值（建议30秒）且有效样本≥20 | 两个不同分钟截止点满足 | 严重 |
| 内存高水位 | 每节点内存≥预警/严重阈值，优先复用现有80%/90%或用户现值 | 预警60秒/严重30秒 | 分级 |
| CPU 高水位 | 每节点整机 CPU≥80%/95%，如有站点现值则复用 | 预警60秒/严重30秒 | 分级；初始建议，需按容量校准 |
| CPU 快速增长 | 当前≥70%，最新完整30秒均值比此前完整60秒均值增加≥30个百分点 | 有效覆盖≥80%且最大缺口≤15秒，再持续30秒 | 预警；不将单点尖峰当持续饱和 |
| 内存快速增长 | 当前内存≥70%，最近3分钟增长≥2个百分点/分钟 | 新鲜有效覆盖满足，再持续30秒 | 预警 |
| 出口接口接近预算 | 已选接口发送速率≥配置安全预算80%/90% | 60秒/30秒 | 分级 |
| 采集异常 | 连续3次上报周期不可读/投递失败，或数据超过有效期 | 一次episode | 数据异常 |

不得默认写死适用于所有服务器的 MiB/s 门槛。站点设置支持填写“请求字节速率预算”与“指定网卡安全预算”，空值禁用相应绝对规则，页面明确“待配置”。

分位数低样本以“样本不足”展示；极端个例仍可列样本/图上标记，不从一个样本推断整个渠道故障。渠道阈值为本新监控规则配置，不改动现有调权/恢复探测的30秒规则。

基线：取当前评估窗口之前5分钟结束的最近60分钟完整1分钟桶中位数；至少30个有效桶，基线为0/缺失时停用倍数条件但允许已配置的绝对规则。故障episode期间冻结基线；基线是参考，不会替换绝对资源高水位保护。

### 6.2 积压风险组合

积压风险是推断，不是队列测量。以同一站点、时间有重叠的新鲜证据组合：

- F：后三档大请求负载规则已触发；<5 MiB合并档用于数量对照，本轮仍不增加大小占比规则。
- L：站点至少一个有足够近期业务量的渠道首响应规则已触发（相关渠道业务量门槛可设，建议≥20条/5分钟）；
- M：任一节点内存高水位或快速增长规则已触发。

组合规则：M 且 (F 或 L) 持续60秒 → “请求积压风险”；F+L+M 同时满足或节点内存达严重线 → 升为严重。独立内存严重告警不必等待组合成立。

CPU 使用独立高水位/快速增长规则，不要求渠道一定慢或内存一定高。CPU 与大请求、完成请求数或渠道变化同屏列出实际时间窗，称“同时观察到”，不能自动判断为解析或 GC 原因。CPU 和内存都达严重线时合并节点资源风险通知，但保留两项独立证据；恢复时 CPU 低于预警线10个百分点持续2分钟，内存按原恢复规则，缺失不得触发恢复。

不能断言 F 与 L 来源于同一请求，也不能把单节点资源异常归因到某个渠道；告警称“同时观察到”，列出实际节点和渠道。请求字节都在结束时落桶时可能出现集中完成峰值，提示“完成日志集中返回亦可导致峰值”。

请求完成率突然下降只作为图上辅助证据，不能区分低流量与挂起；不得单独判恢复或断流故障。若真实在途事件未接入，整体突然挂起可能先由内存/资源告警发现，也可能在资源增长前无法提前告警，这一盲区保持明确。

### 6.3 状态机、去重与恢复

`正常 → 待确认 → 预警 → 严重 → 恢复观察 → 恢复`；数据不足走独立 unknown 状态。

- 每次只由新的源截止时间推进持续计时，重复上报、页面刷新不能累计触发时长。
- 请求大小/速率规则的60秒窗口必须有6个完整10秒桶且最新数据有效；5/6只能展示“部分覆盖”，不能通过按比例外推触发或恢复。缺失不能补零。渠道分钟数据需对应时间覆盖。
- 资源≤20秒视为新鲜；请求最终桶以 source read-through 和观察延迟判断，正常目标≤30秒；渠道默认≤90秒。超过有效期暂停新组合判断，保留已有未恢复状态。
- 恢复阈值：内存低于预警线5个百分点持续2分钟；速率低于触发门槛80%持续2分钟；渠道P95低于预警线80%且样本足够、连续2个新分钟截止点确认。
- 组合中的依赖规则均明确恢复才关闭；证据消失或渠道无流量只能“无新样本/待确认”，不声称渠道恢复。
- 同一站点/节点或渠道/规则只有一个活动episode；严重性升级立即产生事件，默认每15分钟最多提醒一次，恢复通知一次。
- late/backfill 数据只更新历史，不触发“现在”的告警或回填通知。规则版本、阈值快照及证据随episode保存。
- 配置变更以生效时间为边界，关闭旧评估期时记录“规则已变更”，不伪装业务恢复。

## 7. 通知及人工应对

复用已有告警中心、站点通知分流和投递重试。新增请求压力类规则映射，必须检查已有通知选择不能无意扩大到新类别；上线后站点管理员在既有设置中启用。

通知内容示例（模拟值）：

> 请求积压风险 / pinducloud.com.cn / 14:35–14:38
> 节点A内存82%，3分钟增加8个百分点；渠道B首响应P95为22秒（有效样本46）；已记录大请求字节速率达到配置预算的140%。
> 建议先检查渠道B健康备选和入口并发，点击查看同时间段趋势。

只给用户可执行的建议和页面跳转：

| 证据 | 优先建议 |
| --- | --- |
| 单渠道首响应升高、其他渠道正常 | 查看该渠道与健康备选的容量和分组，必要时人工分流 |
| 大请求增加但资源稳定 | 关注趋势、核对大请求来源，避免立即全站限流 |
| 内存快速增长且渠道变慢 | 提前收紧入口并发/重试，观察现有请求排空 |
| 网卡预算接近上限 | 核对该接口业务流向和健康上游容量 |
| 数据缺失 | 先处理采集链路，不能依赖当前“正常”状态 |

首版不执行 NewAPI 改权、限流、重启或取消；现有调权系统仍按原策略运行，告警不能直接触发第二套控制回路。通知外部已发但确认丢失仍可能至少一次重复，继承现有投递语义，不承诺严格恰好一次。

## 8. 存储、接口与权限

### 8.1 表/对象（拟定）

| 对象 | 用途及核心键 |
| --- | --- |
| request_monitor_sources | 站点/实例/来源映射、格式、writer epoch、配置版本、有效期 |
| request_traffic_batches | batch_id与接收时间，事务幂等 |
| request_traffic_10s | source_id + bucket + route_family + status_class；四档计数/字节、大请求摘要及统计版本 |
| request_traffic_1m / 5m | 分钟与长期汇总；按源数据版本重建，不反复相加 |
| request_monitor_health | read-through、解析缺失、积压、丢失、能力版本 |
| request_monitor_samples | 有界大请求样本，仅元数据，sample_id来自来源generation+offset |
| request_pressure_rules / states | 配置与状态、连续满足起点、基线、最后评估源水位 |
| 已有 alerts/events/deliveries | 事件历史与通知，增加规则类型及证据 |

迁移编号实施时取 main 下一个可用号，当前已有122，不预占其他会话编号。新增表/字段兼容旧 Agent，来源未接入显示未接入。

### 8.2 拟定 API

- `POST /api/agent/request-monitor/report`：版本化批次、采集覆盖、资源有效性/可选状态；继承现有 Agent token 身份和实例绑定，不相信payload自行声明站点。
- `GET /api/dashboard/request-pressure/series`：站点、节点、开始/结束、粒度、接口/状态过滤；请求大小与资源各自返回覆盖范围。
- `GET /api/dashboard/request-pressure/channels`：站点、渠道、可选模型、时间窗；返回原生粒度、P50/P95/直方图覆盖和样本数。
- `GET /api/dashboard/request-pressure/events`、`/samples`：游标分页，默认20最大100。
- `GET/PUT /api/dashboard/request-pressure/rules`：站点规则、版本比较、变更审计。

每个series返回 `source_as_of`、`received_at`、`coverage`、`partial`、`quality_reason`、`series_version`、`metric_definition`。单条曲线最多720点，超出自动选更粗粒度；每请求最多6渠道/6节点对比，超过时显式要求选择。

告警只采用未过滤的规则作用域数据，不随某个用户页面筛选改变。HTTP 200但数据旧仍显示 stale。

查看继承监控权限与服务端站点授权；规则修改复用适用的设置权限并审计，必要时增量增加独立权限键。用户无权访问的站点不能从聚合/样本/基线绕过。URL和日志路径等采集信息仅管理员可见。

### 8.3 保留和容量

- 建议10秒数据保留48小时，1分钟14天，5分钟90天；原始元数据样本24小时，告警历史沿用既有设置。
- 每source每10秒保留最大5条大请求样本，附明确sampled=true；不能从样本条数推全站请求总数。
- 幂等批次记录至少保留72小时，大于本地离线缓冲允许重放24小时；旧于边界的报告拒绝并返回明确结果，不因去重记录过期再次累计。
- 无需保存全量访问日志或完整请求内容；存储按时间索引小批删除，不能一笔清全表造成长锁。
- 容量计算按配置维度估算：每节点10秒基础桶8640个/天；若平均4个非空路由/状态组合即34560行/天，索引及四档聚合字段开销必须实测。保留策略与预算在启用页展示，不能假设所有站点低负载。

## 9. 性能和失效保护

- Agent 新增内存目标≤32 MiB，硬预算按独立队列/桶/样本逐项限制；这是实现验收目标，不是现有测量值。
- 单批压缩前≤512 KiB、单源本地持久缓冲≤64 MiB/24小时；达到任一上限先停止保留细样本，再淘汰最旧统计批次并记gap，保护业务资源。
- 单源批量读取预算建议≤5 MiB/s且可配置；跟不上时显示log lag，不无限提速抢磁盘。读取/解析CPU与内存目标用代表性日志压测确定。
- 新功能不写 NewAPI 数据库，不复制源库全表，不依赖本地 Go heap保存全量请求。
- Server 批次幂等与计数更新单事务，按固定键顺序写，有限重试；禁用全局大锁。客户端报告并发最多1路，指数退避带抖动。
- 多实例Server用租约和CAS保护规则状态；同一截止时间只推进一次，不能多进程重复生成episode。
- 页面查询按站点缓存5秒、去重并发；查询不扫描原始日志、不给每条样本补查询用户。
- Server不可用时Agent不阻塞Nginx或NewAPI；独立有限缓冲满后如实丢弃。新资源采样不阻塞原采集/归档/渠道探测。
- rollout初期只采集验证，不让已有机器人立刻发送大量历史或新规则消息。

## 10. 实施分期

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| A：采集与趋势 | req_len解析、可靠游标/批次、10秒聚合、Server查询、请求趋势、渠道多线趋势、来源质量 | 定量回放与多节点去重验证通过；用户可看趋势 |

| C：生产观察校准 | 单节点启用→全部节点，配置预算与通知，观察告警 | 真实采集延迟、开销及噪声有记录；用户验收 |
| 后续：在途增强 | NewAPI开始/渠道尝试/首响应/结束事件，实时在途数量及等待 | 另定协议与NewAPI版本补丁，不能以A/B替代 |

A/B组成第一版完整监控交付，C是部署验收；当前仅设计，不开始这些实现。

后续在途增强需要业务源提供稳定request/attempt ID、节点/用户/渠道关联、开始/读体完成/首响应/结束与取消；有界状态和失联清理必须区分结束和未知。只有拿到这些事件后才加入“未首响应>30秒数、在途大请求数/字节”等指标；这些字节也不直接等同实际内存。

## 11. 验收标准

### 数据正确性

- 给定10,000条混合大小/状态/时间样本，四档数量/字节及大请求摘要正确；小于5 MiB合并第一档。四档相加等于已知大小请求总数，后三档相加等于大请求总数，图例隐藏不改变合计。
- 覆盖5 MiB减1 byte、恰好5/10/20 MiB、各边界减1 byte、零值、无大小、中断、413、超大数值、非法状态和时间偏移；5 MiB减1 byte进入第一档，5/10/20 MiB分别进入第二/三/四档，合法零值属于第一档，缺失不归档。
- timed与JSON各自适配，选一个来源统计时两文件共存不翻倍；不同真实入口不误去重。
- 同一批上报3次、ACK丢失重发、Server重启、Agent在WAL/游标提交各点崩溃后，无重复累计；确实丢失的区间标gap。
- Nginx轮转、copytruncate、半行、缺权限、Server离线恢复及缓冲满行为有故障注入验证。
- 渠道延迟直方图先合并再算分位；请求四档计数/字节分别求和。分钟/5分钟重复rollup不翻倍，晚到数据重算历史。

### 告警正确性

- 新数据持续才触发；重复窗口不累加时间；低样本、缺失、失联不能触发恢复。
- 内存高水位独立触发；组合显示相关性不声称因果；暂停/规则版本变更有独立原因。
- 初始/升级/提醒/恢复每个事件各生成一次内部身份；失败退避重试及至少一次投递语义明确。
- 离线历史回放不群发“当前故障”；多站点/多Server互不串扰。
- 第一版用“大小突增→延迟升高→内存增长”的模拟时间线验证，记录触发时刻；不承诺所有生产事故都可提前发现。

### 页面与性能

- 1440/1920桌面及390宽度可读；渠道最多6线，横轴联动、时间筛选、暂停、无数据/过期/低样本均可辨认。
- 默认趋势为主体，采集时间与刷新时间分开；图例隐藏不改变全站分母。
- 以实际峰值≥2倍的日志回放压力测试；峰值未知时报告使用的固定压测RPS和行长，不宣称生产容量已验收。
- 测量新增Agent常驻内存/CPU、磁盘写入/读取、报告字节量、Server写吞吐与查询P95；新增内存≤32 MiB、默认查询P95≤1秒为目标，未达到时降维/限额后复测。
- 正常链路采集展示P95达到第5.5节目标；全断流时清楚记录现有数据的可见性盲区。

## 12. 发布、部署与回滚

- 精确提交本任务到main，保留已有独立错误统计等本地工作；迁移号按实施时实际main顺延。
- 需配套升级Server/Web/Agent；先Server新增兼容协议和迁移，再单Agent灰度，其余Agent后续升级。旧Agent显示未接入。
- 选择日志路径、确认站点/来源唯一及接口清单；无需为第一版改NewAPI代码或增加请求正文日志。
- `/nginx_status` 和网卡采集在本机环境验证可达/正确后启用，不要求开放端口。
- 首轮关闭新规则外部通知，完成覆盖/延迟验证后按站点显式启用；不发送部署之前的历史事件。
- 回滚先停新通知/采集功能开关，保留新表和历史；旧业务采集继续运行。回退旧Server前先停新报告器，避免反复404重试。
- 正式发布前按项目规则核验前序已发布修复提交包含关系；发布、生产部署、生产验收分别记录。
