# 两任务归档与多维日统计：2026-09-22 确认方案

状态：业务设计已确认；2026-09-23 已新增独立两任务执行器和新控制入口，实际交付边界、表结构及尚未完成的接口见 [全新执行器说明](archive-new-engine.md)。尚未经过真实 MySQL 验收或部署，不能据此判断线上行为。本文覆盖旧设计中四任务、先整理后校验、全量复制逐条计费事实作为必经步骤的规划；现有生产表和迁移脚本仍保持原状。

## 2026-09-23 补充确认：替换执行器与新表命名空间

后端正式任务仅为 `collection`（日志采集）和 `history`（历史处理）。旧四任务模式整体退役，不作为新流程的执行器，也不通过将四个任务合并显示来冒充两个任务。初始化属于升级准备步骤；校验、补齐、整理、封存是历史处理的可恢复步骤，不设置独立任务开关。

原始日志继续使用现有 `logs_YYYYMM` 表名、结构和数据。不得为升级删除、清空、重命名或复制替换这些表；正常采集和历史补齐仍可按业务规则向对应月表写入日志。

新辅助表统一使用 `log_archive_` 前缀。旧 `archive_*`、`log_daily_stats`、`log_monthly_stats` 等辅助表原样保留供核对，不要求删除，不作为新执行器的游标或每日状态来源。下文旧表名是先前职责分析，不能直接作为新实现的物理表名。

新表按职责规划如下，实际字段、索引和事务约束须随实现迁移一并交付：

| 新表 | 职责 |
| --- | --- |
| log_archive_meta | 数据集身份、结构版本、写入租约和防止旧会话继续提交 |
| log_archive_collection | 持续采集的初始化依据、起始 ID、已提交游标、最近提交信息 |
| log_archive_batches | 批次幂等凭证及读取、新增、修改、未变化数量 |
| log_archive_history | 历史处理当前日期、内部步骤、扫描/汇总检查点和本轮截止日期 |
| log_archive_days | 每天的数据状态、数据版本、原始数量、跨日证据和当前有效结果 |
| log_archive_day_versions | 每日封存版本、校验依据与发布的日统计版本 |
| log_archive_daily_stats | 按用户、令牌、模型、渠道、历史价格规则及用户折扣分组的日统计；构建中和已发布结果按版本隔离 |
| log_archive_issues | 具体失败日期、步骤、错误码、涉及日志和重试处理记录 |

不新建逐条日志等量复制的计费事实表，不新建独立月统计作为必经产物。账单按有效日统计汇总，必要时从月表回读原始明细；既有正式账单保持不变。

首次启用新命名空间时，只有在新采集检查点不存在的情况下才读取全部月表的最大 ID 初始化；初始化事务提交后只续跑该检查点。已有月份不代表历史完整，最大 ID 之前的数据交给历史处理校验补齐。旧执行器必须先停止并完成在途事务，再开放新写入；新表命名隔离本身不能阻止旧 Agent 继续向同一月表写入。

迁移验收必须包含：新路径不读写旧辅助表；重启不重复初始化或重置游标；旧四任务接口不能重新启动旧执行器；Server/Agent 不兼容时明确拒绝启动；旧账单查询仍可使用其旧证据；所有 `logs_YYYYMM` 升级前后结构及原有数据保留。

此处表名为职责规划；本轮实现将两个任务检查点原子存入 log_archive_meta.state_json，实际物理表及运行路径以 archive-new-engine.md 为准。新代码尚未迁移或部署到远程。

重建边界（用户补充确认）：保留归档库 `logs_YYYYMM` 完整原始日志，其余归档辅助表允许重建，不要求沿用旧辅助表结构。此范围不包括 Server 已生成的正式账单。实施时应先暂停并确认在途事务结束，重新建立身份和防并发写入保护，再初始化检查点和重建每日数据；不能在运行中直接删除辅助表。本轮页面改造未执行任何远程清表。

## 任务与数据状态

- 日志采集：无检查点时，以同一源数据集全部已有归档月表的最大 ID 初始化；空库从头开始。已有检查点时只续跑检查点。历史补漏不推进持续采集游标。
- 历史处理：按天校验并补齐明细，校验通过后整理多维日统计，再封存。只处理具备已提交跨日证据的历史日期；跨日证据不等于完整性校验通过。
- 每日状态只有采集中、待处理、处理中、已封存、处理失败。步骤、等待原因、错误详情独立保存，不扩展成大量每日状态。
- 某天处理失败记录原因并继续下一天。显示当前处理位置、连续完成边界、失败日期，三者不能混同。
- 迟到新增或修正使当天当前结果失效，重新校验整理。相同日志重放不增加数据版本。

两个任务各自持久化进度；调度器在事务完整结束后交接源库读取权。仅源库读取互斥，归档库整理可与采集并行。4 批采集 / 1 批校验是初始调度建议而非固定业务约束；应保证采集优先但历史校验不会饿死。校验可恢复扫描必须具有稳定边界与版本检查。

## 表的职责

| 表或表族 | 职责 |
| --- | --- |
| logs_YYYYMM | 唯一完整原始日志，保留所有源字段及 other 原文 |
| archive_dataset_meta | 数据集身份、结构与写入会话保护 |
| archive_checkpoints | 采集初始位置、已提交位置和批次关联 |
| archive_batch_receipts | 幂等提交凭证，区分读取、新增、修改、未变条数 |
| archive_days | 日期状态、原始数量快照、数据版本、当前封存关联 |
| 历史处理进度表 | 当前日期、校验/整理检查点、规则版本和具体错误；物理迁移需结合现有表制定 |
| archive_day_versions | 封存版本与校验证据、日汇总关联 |
| 多维日统计表 | 按业务维度、历史计价规则、用户折扣汇总；不能复用旧“每天一行”的结构而不迁移 |
| 现有账单表 | 固化账单结果、结算依据和使用的数据版本 |

不为新流程全量复制一套逐条 billing_facts。既有事实、证据、贡献台账及其账单依赖必须迁移验证后才能退役，不能直接删表。月统计不是必要核心表，月账单汇总有效日统计。

## 多维日统计

逻辑分组键：数据集、日期、封存/构建版本、用户 ID、令牌 ID、模型、渠道 ID、历史计价规则标识、用户模型折扣，以及影响金额和查询语义的其他维度（例如分组、币种和用量口径）。上游关联必须有明确依据，不能用变化后的当前渠道归属悄悄改写历史账单。

同日同模型两种用户折扣必须两行；历史单价、表达式或有效分组倍率不同也不能合并。缺失价格/折扣与显式零值不相同。规则标识应来自规范化快照，不直接以 JSON 原文顺序分组；快照保留在统计结果，哈希只用于索引。

每行包含：

- 请求数、错误数、正常/异常条数。
- 普通输入、输出、缓存读取、缓存写入和 5m/1h 细分，以及实际记录的图像、音频用量；避免总量与细分重复累计。
- 源 quota 合计、用户折前额度合计、减免额度合计、用户实际扣费合计；缺失依据的条数和原因。
- 计价快照、用量解析版本、源数据版本和生成时间。

整理按原始日志逐条解析后累加，不保存全量复制的逐条解析结果。恢复时批次进度与中间累加结果一起提交，避免重复累加。发布前确认日期数据版本未变，原子切换有效日汇总；旧账单不自动跟随切换。

表达式必须按单次请求用量、档位、附加费用和舍入语义处理，不能把全天 Token 相加后执行一次。不同上游规则若无法从汇总充分计算，需回读明细，不虚构精度。

## 用户与上游计费隔离

示例：quota_before_discount=95090，user_model_discount=0.56，discount_quota=41840，quota_after_discount=53250。

- 用户原始扣费模式：核对 logs.quota 与折后扣费，累加每条已舍入结果，不再次乘用户模型折扣。
- 上游折前额度模式：以 95090 为本例基数，再应用上游/渠道结算规则；绝不以 53250 为基数套上游折扣。
- 上游独立价格模式：按实际用量和上游价格计算，用户折前额度也不天然等于上游成本。
- 保存币种、额度换算和结算规则快照。缺少折前额度或历史依据时不能静默拿折后金额替代，也不能将现价冒充历史价格。
- 正式账单保留当时结果及必要依据。封存版本号或摘要本身不能还原后来被修改的原始日志。

## 明细与日统计的显示约定

单条请求明细：直接显示实际适用的输入、输出、缓存读取、缓存写入等单价，以及用户模型折扣、折前金额、减免和实际扣费。无需单独的“计价规则”列。表达式根据该请求用量和命中档位提取适用价格；不能还原固定分项价格时明确缺失或动态计算，不用平均值伪装单价。原表达式仅在展开详情用于核对。

日统计：简短显示分组的计价规则，点击展开完整快照。例如：

- 按量：输入 20 / 输出 100，缓存读 2；用户 5.6 折。
- 按次：0.1/次；用户 8 折。
- 阶梯：≤200K 输入 20 / 输出 100；>200K 输入 40 / 输出 150；用户 5.6 折。

币种、单位必须明确，不展示不透明规则 ID。上游账单展示实际采用的上游结算规则和折扣，不把用户模型折扣作为上游优惠。

## 与当前实现的差距及验收

2026-09-22 页面落地：运行总览、每日数据、设置三个入口；采集和历史处理两组控制映射到现有执行器配置，历史处理暂停同时关闭 organization/verification；全局暂停后单独恢复一组不会自动恢复另一组。日期详情改为页内展示，包含日统计、日志明细入口，当前接口缺失时明确提示，不使用示例或源库数据冒充归档数据。计数与操作来自现有上报，不推测追平状态、连续封存边界或完成百分比。旧内部开关折叠至兼容设置。

此页面改动没有实现新的调度器、先校验后整理顺序、最大 ID 初始化、多维日统计存储及查询、归档明细查询或新账单路径，也没有重建远程表。验证：46 项归档与控制测试通过；生产前端构建通过；本地模拟接口浏览器验证 1440/640 两种宽度、任务暂停请求、日期详情、设置切换通过。

当前存在四任务及旧贡献台账流程；旧 log_daily_stats/log_monthly_stats 只有总量指标；封存事实模板按请求保存记录。这些不等于本方案已经实现。

实施需覆盖：检查点初始化与迁移；可恢复的两任务调度；先校验后日汇总；多维统计新结构及价格/折扣口径；按版本读日统计生成两类账单；明细/汇总展示；旧依赖切换和兼容升级。

关键验收：同日两折扣分行且用户费用不重复打折；上游折前/独立价格两条路径；缓存细分不重复；表达式按请求阶梯及舍入；重试不重复计数；迟到写入使发布失效；缺失计价不冒充零价；既有检查点不被最大 ID 覆盖；账单生成后规则变化不改变旧账单。
