## 核验

- **模型上下文全局表化（038）**：max_context_tokens 是模型属性不是站点属性——新表按 model_name 全局共享，038 用窗口函数从各站点旧表取最新值幂等回填（CREATE IF NOT EXISTS + INSERT IGNORE，CT 库 MySQL 8 支持）；PutBillingModelMetadata 事务双写（全局上下文 + 站点可用性）；读取 COALESCE 全局值。记档：per-instance 表的 max_context_tokens 列成死列，清理候选。
- **生成预检（行为变更）**：创建任务前同步 newapi 模型清单，任何配置模型缺上下文 → 409 `billing_model_context_missing` 带缺失清单，不建任务；runner 内对日志出现的模型二次硬校验（防已退役但有历史日志的模型漏网）——缺失时任务显式失败，配置后重试可恢复。语义上把"unknown context accepted"的宽松口径收紧为强制配置，异常判定（超上下文）从此无盲区。**验收方补 handler 级测试**（交付无测试）：409 载荷形状 + 不建任务 + 补齐后 202 放行三断言。
- **异常单实际扣费金额（037）**：actual_amount = GREATEST(quota,0)/QuotaPerUnit 六位舍入，任务收尾拿 ratio 快照统一回填该 job 全部异常行；汇总/明细/CSV 的"异常金额"从参考应收额改为**实际扣费额**（回答"异常订单实际扣了多少钱"），参考金额列在 CSV 保留——两口径并存无信息丢失；前端标签"异常总金额"与新语义相容。
- request_key 升 v6：正确（v5 未上过生产，无叠加，从 rc26 升级仍只重生成一次）。
- P3 记档：409 的缺失模型清单前端未展示（用户只见错误码文案），下次动账单页顺手把清单渲染出来；预检对每次生成 POST 多一次 newapi options/models 读取，低频可接受。
