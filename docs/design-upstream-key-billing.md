# 上游渠道 key 账单——设计讨论稿（2026-08-18,用户发起,待拍板）

## 1. 需求

现行渠道组织是"一个模型一个渠道",同一个真实上游渠道 key 对应 CT/newapi 里的多个渠道。与上游对账需要**按上游 key 汇总的完整账单**（= 多个成员渠道账单的整合视图）。

## 2. 现状地基（已核实）

- 渠道维度账单数据实存:`billing_channel_daily_versions`（渠道×模型×分组×档位×天,job 版本化,激活版本查询与按 job 查询两条路径齐备）——**上游账单=成员渠道 IN 查询+Go 合并,无需新聚合/重生成**;
- newapi `channels` 表有 `key`/`base_url` 列（源码 model/channel.go 实证）;CT 整库只读账号可读 channels（渠道名 join 既有用法）;
- 约束:CT 从不存渠道 key 明文（写路径 delete key 的既有原则）,方案不得破例。

## 3. 方案:key 指纹自动分组

分组依据=**newapi 库内计算的 key 哈希**（`SHA2(key,256)`,SQL 内完成,明文不出库,CT 只见不可逆指纹）。同 key 渠道自动同组,零人工维护,新渠道自动归组。

否决的备选:手工分组表（维护成本随渠道增删,易漂移）;按 base_url 分组（同上游多账号会混,粒度错）。

读路径:

1. 分组列表:现查 newapi 得 channel_id→指纹映射,join 渠道账单聚合 → 每组一行（成员数/区间合计 请求数/prompt/completion/cache tokens/quota）;
2. 组详情:日×模型明细（一模型一渠道 → 模型维度天然=成员分解）+成员渠道小计对照表;
3. 导出:合并工作簿/CSV,复用渠道导出机件;
4. 读闸:沿用渠道账单 job 绑定语义（最新 complete 任务,409 语义一致）。

**对账口径**:上游按其自身价格开票,主字段=请求数/分模型 tokens/按天;quota 金额仅参考列。界面按此主次呈现。
